# Нагрузка: LT-1..LT-6 (docs/06 §4)

Здесь живут **LT-1 и LT-3** — два профиля, которым не нужен ончейн: LT-1 грузит API, LT-3 измеряет
индексатор. Остальные строки таблицы §4 требуют стенда, и честнее назвать их отсутствующими, чем положить в
репозиторий скрипт, который «тоже что-то меряет».

## LT-1 · API (k6)

Пороги взяты из `docs/06` §1.3/§4, а не отсюда: p95 ≤ 150 мс на кэшируемых чтениях, p95 ≤ 250 мс на
`/me/*` при 300 rps, ошибок < 0.1 %, и профиль злоупотребления (H3) обязан отвечать **корректный** 429
(`Retry-After`, никаких 5xx и никаких обрывов соединения).

```bash
# 1. стенд: прод-топология из compose (nginx + api + redis), либо локально.
#    RATE_LIMIT=0 обязателен: бюджет чтения — 600 мин/IP (backend/src/ratelimit.ts), профиль на 500 rps
#    с одного адреса упирается в 429, а не в читаемый путь; сама корректность 429 закрыта юнит-гейтом
#    T-B-40 (backend/test/security.test.ts). В проде RATE_LIMIT=0 не стартует (assertProductionConfig).
RATE_LIMIT=0 PORT=8787 npm run backend:start   # или docker compose -f ops/deploy/docker-compose.yaml up -d

# 2. сессия для авторизованного сценария (иначе /me просто пропускается — см. ниже)
#    stdout = cookie, stderr = строка K6_CSRF=… (токен для X-CSRF-Token на /packs/quote)
LT1_BASE=http://127.0.0.1:8787 node scripts/load/login.mjs > /tmp/cookie 2> /tmp/login.err

# 3. прогон (10 % профиля = 500 rps, 4 минуты плато)
docker run --rm -i --network=host -v "$PWD:/s" -v /tmp:/tmp \
  -e K6_SESSION="$(cat /tmp/cookie)" -e K6_CSRF="$(sed -n 's/^K6_CSRF=//p' /tmp/login.err)" \
  grafana/k6:latest run /s/scripts/load/lt1.js
```

Переменные: `K6_BASE_URL` (по умолчанию `http://127.0.0.1:8787/v1`), `K6_READ_RPS`, `K6_ME_RPS`,
`K6_RAMP_S`, `K6_PLATEAU_S`, `K6_ABUSE_VUS`, `K6_SESSION`, `K6_CSRF`, `LT1_KEYPAIR` (файл с JSON-массивом 32/64
байт — если нужен конкретный кошелёк, а не эфемерный).

Три вещи, которые легко понять неверно:

- **`/me` без сессии не меряется «как-нибудь»**. `login.mjs` делает полноценный SIWS-хендшейк (ed25519 в
  k6 невозможен, поэтому подпись делается здесь), и если куки не передана — сценарий `me` **не создаётся**,
  а не молча получает 401. Метрика «p95 авторизованного чтения» против 401 хуже, чем отсутствие метрики.
  Эфемерный кошелёк по умолчанию — не лень, а решение: нагрузочному профилю не нужны средства, а «тестовый
  сид» в репозитории — это способ потерять ключ.
- **401/403/503 на `/packs/quote` засчитаны как правильный ответ.** Без переданного `K6_CSRF` мутация
  честно отвечает 403 (double-submit, `backend/src/auth.ts`), без Pyth-пушера в контуре 503
  `price_unavailable` — это то, что эндпоинт и должен делать (см. `backend/src/pyth.ts`); считать это
  «ошибкой под нагрузкой» значит получить красный ночной прогон по причине, к нагрузке не относящейся.
- **один процесс API не выполнит профиль на 5 000 rps**, и это не баг скрипта: у цели 2 000 rps из
  `docs/06` §1.3 за спиной два условия, которых у одиночного `node:sqlite`-процесса нет (Postgres-слой и
  общий Redis-стор лимитов — `docs/09` §4.1–4.3). Прогон на одной ноде даёт нижнюю оценку, а не провал гейта.

## LT-3 · индексатор (`npm run load:lt3`)

Вопрос не «выдержит ли индексатор нагрузку» (его держит RPC), а **сколько стоит восстановление read-model**:
`npm run backend:rebuild` — это и есть ответ оператора на испорченную проекцию, и если он стоит 40 минут,
ответ неверный. Порог RPO у read-model нулевой по построению (источник истины — цепь), поэтому цифра
прогона = длительность окна, в котором UI показывает устаревшее состояние.

```bash
npm run load:lt3                                  # 1M событий, ~9 минут ingest + пересборка
LT3_EVENTS=250000 npm run load:lt3                 # ночной профиль (job `replay` в CI)
LT3_KEEP=1 npm run load:lt3                         # не удалять БД: путь печатается в конце
LT3_MIN_EVENTS_PER_S=2000 npm run load:lt3          # порог, на котором падает job (CI ставит низкий — runner'ы общие)
```

Печатается: число событий, дедублицированные и проигнорированные (`err != null`) транзакции, размер БД,
throughput живого индексирования и пересборки, экстраполяция на 1M, и построчные размеры 21 таблицы
проекции — чтобы «rebuild подешевел» нельзя было объяснить тем, что corpus стал меньше.

Корректность живёт не здесь, а в `backend/test/replay.test.ts` (30 тестов, PR-гейт): побайтовая
идентичность «проиндексировано вживую» ⇄ «пересобрано из `events_raw`», no-op на повторном прогоне,
рестарт через файловую БД с курсором, и инварианты «одна строка проекции на событие». Корпус один и тот же
(`backend/test/chainHistory.ts`, детерминированный по сиду), поэтому замер и проверка описывают одни и те
же данные. Найденное тиром (потеря block time в проекциях, `docs/09` §4.9) было найдим именно из-за такой
связки: тест сравнивает два пути, а не сверяет один с самим собой.

## Чего здесь нет, и почему

| Строка §4 | Почему скрипта нет |
|---|---|
| LT-2a pack storm (localnet) | нужен `solana-test-validator` + генератор транзакций (`scripts/load/packstorm.ts`), и `sb_mock`-сборка программ: в этой среде нет ни `cargo`, ни `anchor`, ни валидатора (`docs/09` §8) |
| LT-2b pack storm (devnet) | то же + реальные очереди Switchboard (`Aio4…`/`EYiA…`) и оплаченный devnet-payer; **G-3 soak-бот** (`scripts/load/soak-g3.ts`) — 14 дней, ≥10 000 паков |
| LT-2c dress rehearsal | mainnet, 200 паков командными кошельками — только руками |
| LT-3 indexer (остаток) | `npm run load:lt3` и `backend/test/replay.test.ts` закрывают всё, что измеримо без цепи (см. секцию ниже). Не измеримо отсюда: лаг p95 при 50 tx/с, 200 tx/с на реальном `backfill`, WS-мок провайдера и память под настоящим RPC-потоком |
| LT-4 crank | 10 000 pending в очереди + обрывы RPC — требует LT-2a-стенда |
| LT-5 PvP | 5 000 в матчмейкинге + wager-оракул 5 resolve/с — требует аренда с ключами |
| LT-6 chaos | остановка киперов/индексатора/Pyth на живом контуре |

Порядок: LT-1 здесь и сейчас (он ничего не ждёт), LT-2a — сразу после G-0 (первая зелёная `anchor build`),
остальное — вместе с devnet-стендом.
