# Возраст, доступ, возвраты и персональные данные — текущая реализация

Дата: 2026-09-29. Ветка: `arena/01a0ea01-guttercaps`.

## Решения владельца и границы

1. **Юридический блокиратор сборки/деплоя удалён.** Не нужно заполнять оператора,
   страны и заключения для mainnet-сборки. Удалены вызовы из Vite, image CI,
   `ops:buildenv`, `setup`, `ops:release`, лишнее копирование legal manifest в client image.
   Program-ID, oracle/security guards, отсутствие sourcemap и защиты секретов сохранены.
2. **По последнему решению владельца проверки возраста и географии временно выключены
   для всех по умолчанию, включая production.** Модуль сохранён для повторного включения.
   При включении возраст проверяется **по заявленной дате рождения**, не через KYC/провайдера.
   Это не независимое установление возраста/личности. Новая дата в форме может быть ложной,
   новый кошелёк может обходить ограничения декларации — данный метод не решает эти проблемы.
3. Возвраты реализованы как **обращения**, без одобрения суммы, подписи treasury-транзакции,
   автоматической выплаты или фиктивного статуса «возвращено». Старый on-chain stale-pack
   cancel/refund остаётся без изменений.
4. Прямые вызовы публичных программ сторонним клиентом не запрещены. Ни HTTP-проверка,
   ни настройка страны, ни проверка перед подписью не являются on-chain authorization.
5. `LEGAL_REVIEWED=false`. Optional `npm run legal:check` всё ещё сообщает об отсутствующих
   согласованиях и может вернуть 1, **но никакая сборка/команда релиза его не вызывает**.
   Владелец принял решение о снятии технического стопа, а не получил юридическое заключение.

## Интерфейс

- `/account/rights` — «Возраст, возвраты и данные», доступен из профиля и юридических страниц.
- `/admin/rights` — очередь оператора, ссылка из админ-панели. Backend требует SIWS,
  `ADMIN_WALLETS` и CSRF; скрытая кнопка не считается проверкой доступа.
- Все новые системные подписи и ошибки переведены на EN/RU/PT/ES/VI/ID/FIL.
  Текст обращения и ответ сотрудника сохраняются в оригинале, не машинно переводятся.
- Возраст/страна не блокируют подачу обращений, чтение ответов и запросы прав.
- Нужны действующий кошелёк/SIWS. **Внешний контакт и альтернативный канал для утративших
  кошелёк ещё должен предоставить оператор**; вымышленный email не создан.
- Демо хранит обращения только в памяти страницы и не является рабочей поддержкой.

## Возраст и доступ

Настройки: `backend/access-policy.json`, включение: `COMPLIANCE_ENFORCE`.

- `0` — **текущий default во всех окружениях и Docker Compose**. Декларации/обращения
  доступны, но age/geo не отказывают в новых действиях: неизвестная страна, BE/NL, отсутствие
  декларации и ранее отклонённая декларация сами по себе не блокируют доступ.
  UI показывает, что проверки отключены.
- `1` — явное повторное включение runtime-проверок. Требуется корректный источник страны.
- Активная privacy restriction действует независимо от флага age/geo.
- Неверный флаг или повреждённый policy JSON не интерпретируются как разрешение.

Для режима без age/geo оставить также `GEO_GATE=off` (независимый прежний gate магазина),
`VITE_FLAG_AGE_GATE=false` и `VITE_FLAG_GEO_GATE=false` (прежние клиентские блокировки).
`GEO_UNKNOWN=allow` — текущий legacy default. Правила BE/NL и minimumAge=18 сохранены
в policy, но не применяются к допуску при выключенных проверках. Декларации не удаляются.

Изменены настройки проекта, **не окружение уже развёрнутого сервера**. Если в нём явно
заданы `COMPLIANCE_ENFORCE=1`/`GEO_GATE=shop`, они имеют приоритет над default: нужно задать
`0`/`off` и пересоздать API-контейнер; клиентские VITE-флаги применяются при сборке образа.
Требование возраста в договорном тексте не отменено отключением технического контроля.

Поля policy (возрастные/территориальные правила применяются при включении enforcement):

| Поле | Поведение |
|---|---|
| `revision` | При изменении возрастных условий повысить версию: старая декларация потребует обновления |
| `minimumAge` | Сейчас 18; не обещает, что этого достаточно в каждой юрисдикции |
| `countryMinimumAge` | Порог выше общего для конкретного ISO-кода; ниже общего не допускается |
| `declarationDays` | Сейчас 365; повторное подтверждение после истечения |
| `deniedRetryDays` | Сейчас 30; отказ нельзя тут же переписать взрослой датой |
| `closedRequestRetentionDays` | Сейчас 180; применяется только отдельной командой к закрытым обращениям, с исключениями |
| `features.*.allow` | `null` — любой распознанный ISO-код кроме deny; `[]` — ни один; массив кодов — allowlist |
| `features.*.deny` | Запрет имеет приоритет над allow |

Функции: packs, market, staking, arena, rewards, services, fusion. **Начальная policy
сохраняет только прежний запрет BE/NL для packs**, остальные deny пусты, allow=null.
Это техническая исходная настройка, **не утверждённый международный список рынков**.
Для реальной ограниченной географии владелец должен задать конкретные allow/deny и
пороги. Policy читается при запуске API; после изменения нужен перезапуск/новый образ.

При включённом enforcement неизвестная/недоверенная страна означает отказ. Используются
существующие `GEO_TRUST_HEADER` и `GEO_COUNTRY_HEADER` (по умолчанию `x-geo-country`).
**Нельзя просто довериться публичному заголовку:** ограничить доступ к origin, принимать
трафик только от настроенного edge, перезаписывающего country header. Иначе клиент может
его подделать. Включение флага само по себе не создаёт эту сетевую границу доверия.
`GEO_GATE=shop` — прежний дополнительный gate; он не заменяет новую feature policy.

Возраст рассчитывается по UTC-календарю, с проверкой реальной даты и дня рождения.
Для 29 февраля в невисокосный год порог достигается 1 марта. Различия местных правил
нужно отдельно оценить. В БД сохраняются wallet, passed, threshold, policy revision,
declared/expiry timestamps — **не дата, не год рождения, не паспорт**. Не включать запись
тел запросов для этих маршрутов в CDN/WAF/APM/proxy. Результат не называть «verified».
При ошибке пользователь подаёт correction case; после review оператор может сбросить
декларацию, но пользователь всё равно должен подать новую. Это не выдача верификации.

Где технически проверяется:

- Сервер: pack quotes, новая очередь arena, новые login rewards; чтение quests не
  начисляет login/не обновляет дневную запись, если доступ не разрешён.
- Наш клиент: перед подготовкой и перед подписью новой транзакции `sendTx` проверяет
  feature + совпадение SIWS wallet с payer. Отказ/API failure не игнорируются.
- Отмены, unstaking, завершение уже оплаченного открытия/слияния и получение ранее
  заработанного по существующим proofs не требуют eligibility API. Смешанная транзакция
  «выход + новая покупка» всё равно проверяется.
- Сторонние chain clients, операторы reward/indexer и blockchain history не превращены
  этим в глобально геофенсированную систему. Для такой модели нужны изменения протокола,
  миграционная стратегия и отдельный security review.

## Обращения и возвраты

Типы: refund, withdrawal (отказ от договора), access, erase, correct, restrict, object.
Статусы: received → in_review/answered/closed; ответ пользователя возвращает открытое
обращение в received. На закрытое дело создаётся новое обращение. Перед ответом оператор
видит version; устаревшее изменение получает 409 вместо перезаписи.

- UUID, wallet-scoped idempotency key, hash тела, время, язык, response target, версия policy.
- До 20 открытых обращений на wallet, до 50 сообщений пользователя на кейс, текст ≤4000
  символов; общий API rate limit и CSRF остаются включены. Это ограничение ресурса, не отказ
  от законного права: оператору нужен альтернативный канал и процедура обработки превышений.
- Пользователь видит свои обращения; чужой ID возвращает 404. API не принимает владельца
  дела из пользовательского текста. Мутации дополнительно связываются с intended wallet.
- Скачать JSON-подтверждение и переписку можно из UI. Email-доставка не подключена.
  Юридическую достаточность такого подтверждения/канала и дополнительные обязательные
  формы отказа должен определить оператор по рынку — одна кнопка не закрывает всё право.
- Для privacy target задан **один календарный месяц**, не 30 дней; для остальных — внутренний
  target 14 дней, не обещание срока законного возврата. Продление срока, национальные правила,
  жалобы, выплаты и уведомления требуют действий оператора; автоматического legal clearance нет.
- Transaction signature — только ссылка. Не проверяется право на возврат, не принимается
  произвольная сумма и не создаётся вывод. Решение/платёж оформляются отдельно.
- В staff queue выводятся до 200 записей, открытые и с ранними сроками первыми; пользователь
  видит до 100, открытые первыми. Нужны ежедневная обработка очереди и внешний канал для
  обращений, не доступных через текущий интерфейс. Это не полнофункциональная helpdesk CRM.
- Текст ответов оператора доступен пользователю. Приватные заметки/паспортные вложения сюда
  не отправлять. `admin_audit` получает действие/ID/actor/version, но **не дубликат переписки**.
  Клиент не раскрывает игроку личный wallet сотрудника, обозначая его как «Оператор».

## Данные, ограничение и удаление

1. **Self-service export** (POST с CSRF, логин не старше 15 минут): профиль, декларация,
   маркер ограничения, обращения/переписка. Это подписано как subset. Нет CSRF/session
   secrets, чужих записей или wallet сотрудника. Для полного access review есть отдельный
   тип обращения; все журналы/процессоры автоматически не собираются.
2. **Restrict/object** сразу оставляют marker и запрещают новые действия через описанные
   first-party механизмы. Не прекращают нужную аутентификацию/работу с правами и не удаляют
   обязательную историю. После review correction case оператор может возобновить обработку;
   возобновление не восстанавливает удалённые данные и не подтверждает возраст.
3. **Erase profile** доступен только allowlisted оператору на `privacy_erase` в `in_review`,
   с актуальной version, явным подтверждением UI и объяснением пользователю. Удаляются
   handle/country, handle history/reservations, sessions и SIWS nonces; остаётся restriction
   marker. Статус становится **answered**, не «все данные удалены».
4. **Сохраняются для отдельной оценки:** chain/projections, финансовые и антифрод-записи,
   age declaration, rights case, marker, внешние логи и backups. Основание/сроки для этих
   категорий ещё должен определить оператор. Нельзя обещать полное стирание Solana.
5. Новые таблицы исключены из projection rebuild. Re-indexing не сбрасывает сам ledger,
   но это не гарантия удаления public-chain данных или всех их копий.

### Плановое обслуживание — нужно установить расписание

Команды реализованы, **не запускаются автоматически и не выполнялись на реальных данных**:

```bash
# Из корня репозитория, с правильным DB_PATH и резервной копией:
npm run privacy:retention -- --execute
npm run privacy:reapply -- --execute

# В production-контейнере с уже настроенным /data и DB_PATH:
docker compose -f ops/deploy/docker-compose.yaml exec -T api \
  node --import tsx backend/src/privacy-maintenance.ts retention --execute
```

- Retention удаляет до 1000 закрытых кейсов за проход только после заданного срока,
  включая их сообщения; открытые, действующие hold и связанные restriction markers
  исключаются. `holdUntil` задаётся через admin reply API с объяснением; не продлевается
  автоматически. Истёкшие декларации удаляются через 30 дней после expiry, кроме
  открытых/held cases и markers; истёкшие sessions/nonces тоже очищаются.
- Назначить расписание (например, ежедневный job), проверить env/DB_PATH, логировать
  только счётчики и контролировать exit code. Политика для старых финансовых/antifraud/
  audit/log/backup данных этим job **не реализована**.
- После восстановления backup **до публичного открытия** восстановить актуальный
  `privacy_restrictions` ledger из защищённой актуальной копии, затем `privacy:reapply`.
  Старый backup сам по себе не содержит запросов, поступивших после его создания.
  Автоматической синхронизации с внешним erasure ledger здесь нет: это обязательный шаг
  оператора. Resumed markers не применяют старое удаление к новым данным повторно.
- Job не уничтожает backup-файлы, не очищает CDN/RPC-провайдеров и не выполняет legal-hold
  assessment. Эти операции и срок хранения самой доказательной базы должны быть согласованы.

## Необходимая операционная настройка

Оператору остаются: значения country policy/порогов, защищённый edge, `ADMIN_WALLETS`,
рабочая очередь и ответственные/сроки, внешний контакт, расписание maintenance и безопасное
восстановление ledger. Выбор юрисдикции, возрастная достаточность, основания обработки,
retention для оставшихся категорий, consumer remedies и лицензии не установлены кодом.

Ни реальный деплой, ни выплаты, ни реальное удаление пользовательских данных в этой работе
не выполнялись. Новые SQL-таблицы добавляются при старте БД; старые записи и экономические
параметры не мигрируются разрушительно. Mainnet и mock-сборки проверены отдельно; наличие
собранного mainnet-клиента не означает публикацию или готовность контрактов к запуску.
