Механизм: список `SBFPINS` в `scripts/ci-cargo-lock.sh` (политика «каждый пакет в локе читаем самым старым cargo, которым мы собираем»), проверка — `scripts/ci-sbf-toolchain-check.sh`, которую `programs` исполняет *до* `anchor build`, а `lockfile.yml` — *до* коммита лока. Класс будет возвращаться при каждом обновлении зависимостей, поэтому это гейт, а не один патч. **Дырка в механизме, найденная тем же прогоном:** guard `lockfile.yml` спрашивает «соответствует ли лок манифестам» (`--locked`) — и лок, который *соответствует, но нечитаем*, получает «работы нет»: автовосстановления для этого класса нет, потому что пин-машина запускается только когда лок нужен. Два варианта закрыть это, выбран второй: (1) перенести решение в джоб `generate` (он уже стоит в нужном образе) ценой полной компиляции workspace на каждом пуше; (2) оставить красный `programs` и назвать в аннотации команду перезапуска — `gh workflow run lockfile.yml -f refresh=true` — которая и есть штатный путь пересборки лока. Из этой среды dispatch недоступен (токен интеграции отвечает `403 Resource not accessible by integration`), поэтому строка говорит, кто должен нажать её руками: **Дырка закрыта тем же вечером, без dispatch:** лок — единственный артефакт, который `lockfile.yml` умеет производить сам, и его удаление — это тот же триггер через открытую дверь (guard видит «лока нет», `generate` резолвит и пинит, включая `SBFPINS`, доказывает `cargo check --workspace --all-targets` *и* `ci-sbf-toolchain-check.sh`, `deliver` коммитит результат). Что сделано: (1) cargo ищется `find`'ом по дереву установки с правилом «тот, что отвечает другой версией, чем cargo из PATH» — эта разница и есть определение «тулчейна, которым собирается .so», и оно переживёт переезд файла; режим `--probe` отдаёт путь и версию машиной читаемо; (2) «solana есть, cargo рядом не найден» больше не `rc=2`: это регрессия поиска в скрипте, и она становится `rc=1` (жёсткий отказ) — гейт, который не видит граф там, где граф собирается, не имеет права выглядеть зелёным; «solana вообще не на PATH» остаётся `rc=2`; (3) вместо ручного списка — **обход** в `ci-cargo-lock.sh`: спросить найденный cargo, вынуть имя пакета из его же отказа, взять из индекса crates.io новейшую версию того же мажора строго ниже виновника с `rust_version ≤` версии SBF-cargo, `cargo update -p name@ver --precise`, до 8 шагов, каждая строка журнала — `sbf-autopin:`; если выбрать нечем, аннотация уже содержит готовую строку для `SBFPINS` (формат списка — `<crate> <мажор.минор> <пин>`, потому что матчинг идёт по `^crate v<line>\.`; подсказать полную версию означало бы выдать совет, который список не видит); (4) `zeroize 1.9 1.8.2` записан в `SBFPINS` явно — страховка на тот же случай, который и сломал прогон: если cargo снова не найдётся, обход не спросит ничего, а curated-строка пинится репозиторным cargo и работает. ## 2. Program IDs: «placeholder» превращается в задачу миграции

`Anchor.toml` содержит `[programs.localnet]`, `[programs.devnet]` и `[programs.mainnet]` **с одинаковыми id**;
`[provider] cluster = "devnet"`. Все четыре id подписаны как «Placeholder IDs —
run `anchor keys sync` after the first `anchor build`» + `REGENERATE THE IDS BEFORE MAINNET` (этот комментарий —
не гейт; гейт — `program-ids -- guard-mainnet`, см. ниже).

Последствия, которые надо закрыть **до** деплоя, а не после:

1. `anchor keys sync` перепишет `declare_id!` на id того keypair'а, который лежит в `~/.config/solana/id.json`
   разработчика. Для прода это неприемлемо: id должен быть выведен из холодного keypair'а, которым
   владеет мультисиг. Правильный порядок: сгенерировать 4 keypair'а → положить id в `Anchor.toml`
   (devnet и mainnet — разные секции!) → *не* запускать `keys sync`, а проверять `solana-keygen pubkey`
   по `target/deploy/<p>-keypair.json`.
2. Смену id надо синхронно сделать во всех местах из контракта `ID_SITES` (`scripts/program-ids.ts` —
   сейчас 13 файлов: `declare_id!`, `chip.rs`, `Anchor.toml`, клиент/бэкенд, `setup.ts`, `create-lut.ts`,
   `ci.yml`, `docs/08`; живой список показывает `apply --dry-run`). Руками не править — только `apply`:
   `check` падает на любом расхождении с `declare_id!`, а файл из `ID_SITES`, потерявший id (переименование),
   падает отдельно и громко.
3. Один и тот же id в devnet и mainnet — **принятое решение** (один холодный keypair на обе сети:
   единый `declare_id!` и гейт `check` требуют совпадения всех трёх секций — разные id на mainnet
   потребовали бы отдельной mainnet-сборки). Цена решения: **утечка devnet-ключа = компрометация прода**,
   поэтому keypair едет в Squads/HSM шагом церемонии (шаги печатает `program-ids -- new`), а `guard-mainnet`
   сверяет mainnet с множеством плейсхолдеров, а не с devnet: равенство mainnet==devnet после церемонии —
   норма, манифест фиксирует его явно.

## 3. CI/CD: нет ни одного работающего конвейера

### 3.1 CI мёртв по финансовой причине (не из-за кода)
Последние 10 прогонов — все `failure`, длительность 6–9 с. Аннотации GitHub API:
*«The job was not started because recent account payments have failed or your spending limit needs to be
increased»*. Т.е. **в истории проекта нет ни одного зелёного прогона** — ни `economy`, ни `client`,
ни `backend` (локально они проходят: см. §3.4). До G-0: оплатить Actions/поднять self-hosted runner,
иначе «сборка программ» не произойдёт никогда.

### 3.2 Конвейера деплоя нет вообще
В `.github/workflows/` только `ci.yml`. Нет: сборки и публикации образов, деплоя клиента (`dist/`)
и бэкенда, `solana-verify submit` (для сверки on-chain bytecode), миграций БД, rollout/rollback,
управления секретами (нет ни `secrets.` в workflow, ни `.env.example` у бэкенда при **79** env-переменных).

### 3.3 CI врёт «зелёным» там, где тесты не запускались
- job `programs` и job `localnet` помечены `continue-on-error: true` → красная сборка программ не блокирует PR (снято: `programs` с `47b6ee4` блокирующий, `continue-on-error` остались только у трёх ночных джобов — см. §3.5);
- localnet-сьют при отсутствии `.so` **скипает всё и выходит с кодом 0**:
  `tests/localnet/*.spec.ts` → `describe.skipIf(!bins.ok && !process.env.LOCALNET_RPC)`.
  Локально: `Test Files 10 skipped (11), Tests 11 passed / 80 skipped (91)`, `EXIT=0`.
- `npm run test:validator` (`anchor test`) в CI не запускается вовсе.
Минимальная правка: fail-fast (`throw`) при отсутствии бинарей + отдельный guard `--reporters=json`
с проверкой «выполнено > 0», и снятие `continue-on-error` сразу после первого зелёного

**Прочитать красный прогон — часть того же гейта, а не вежливость.** Localnet-джоба — единственное место, где
отказ это *много* отказов (83 сценария на пять программ), и её лог так же недостижим из терминала, как лог
`programs`. Поэтому у джобы два канала наружу: `scripts/ci-surface-log.sh` (окна самого вывода) и
`scripts/ci-surface-junit.sh` (по аннотации на `<failure>`/`<error>` из junit-отчёта: имя теста, позиция из
`--> path:line`, тело с диффом; не больше 12, и строка учёта с полными числами — «12 из 23» должно читаться
иначе, чем «все»). Отдельно, потому что на этом скрипте поймались три дефекта одного класса: итоги надо брать
из внешнего `<testsuites>`, а не из последнего `<testsuite>` (иначе «4 test(s)» про сюиту из 83), искать
атрибут `name="` с ведущим пробелом (иначе он матчится внутри `classname="`), и экранировать `%` до вставки
`%0A`, иначе читается `%250A`. Проверяется `npm run selftest:junit` (21 проверка, 4 сценария; песочница —
temp-каталог скрипта, и это тоже записано: поддельный `Cargo.lock` в прошлый раз приехал именно из фикстуры,
написанной в корень).

Смысл этого канала подтвердился сразу же: в прогоне 79 `localnet` впервые исполнился и упал на `run
suite`, и единственным, что оттуда выехало, было `Process completed with exit code 1`, хотя полный отчёт лежал
в артефакте `localnet-junit` рядышком и прочесть его было нечем.

И правило, оплаченное прогонами 76–78: **прежде чем чинить то, что нашёл красный шаг, надо проверить, что его

скрипта (у него 0 и 1), а код node на отвергнутый флаг `--experimental-strip-types` в контейнере якоря; лог в

_solana_-тулчейн, потому что это вопрос к дереву исходников, а не к сборке. `programs`.
