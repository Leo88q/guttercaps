## Фаза 0. Переключатель фаз (фундамент, поведение не меняется)

- ☑ **0.1 Backend-флаг фазы.** `LAUNCH_PHASE=full|g` в `backend/src/config.ts`
  (по умолчанию `full`), проброс в health/admin-статус.
  Приёмка: backend-тест — при `g` конфиг читается, при мусоре — отказ старта.
- ☑ **0.2 Client-флаг фазы.** `VITE_LAUNCH_PHASE` → `FLAGS.launchPhase`
  (`client/src/app/config.ts`), по умолчанию `full`.
  Приёмка: typecheck; клиент без флага ведёт себя как раньше (все тесты зелёные).
- ☑ **0.3 Единая точка ветвления.** Список мест, где клиент/бэкенд обязаны
  смотреть на фазу (покупка пака, слияние, стейкинг, маркет), зафиксирован
  в этом документе (§6); никаких `if` по фазам вне этого списка.
  Приёмка: grep по `launchPhase` даёт только перечисленные места.

## Фаза 1. Ончейн-минимум (скрипт, devnet → mainnet)

- ◐ **1.1 `scripts/setup-minimal.ts`.** Отдельный скрипт (существующий
  `setup.ts` не трогаем): минт $CG (mainnet — через мультисиг, как требует
  текущий setup), ОДНО общее дерево Bubblegum depth 20 / buffer 64 /
  canopy 0, TreeConfig, MPL Core коллекции ×8, казначейские ATA — лениво.
  Приёмка: `DRY_RUN=1` печатает план и смету (дерево 44 280 Б ≈ 0.2256 SOL
  при ставке 5 080.65), ни одной транзакции.
- ☑ **1.2 Тесты сметы.** Юнит-тест формулы размера дерева и ренты
  (синк с `cmtAccountSize` из `scripts/setup.ts`).
  Приёмка: тест в CI; цифры сходятся с §6 плана фаз.
- ☑ **1.3 Env-выход.** Скрипт печатает готовый блок env для backend/client
  (дерево, минт, коллекции, казна).
  Приёмка: вывод копируется в `.env` без ручных правок.
- ☐ **1.4 Devnet-прогон** (на машине владельца): дерево и коллекции созданы,
  тестовый минт cNFT виден в DAS.
  Приёмка: asset id тестовой фишки + ссылка explorer в задаче.

## Фаза 2. Бэкенд: заказы и оплата (ядро фазы Г)

- ☑ **2.1 Заказы паков.** Таблица `pack_orders` (id, wallet, sku, currency,
  amount, memo, status, tx sig, created/expires) + миграция в стиле текущих
  таблиц бэкенда. API: `POST /packs/order` (создать), `GET /packs/order/:id`.
  Приёмка: backend-тесты — создание, идемпотентность по id, протухание заказа.
- ☑ **2.2 Детект оплаты.** Индексатор: перевод на казну с memo заказа →
  `paid` (сумма/валюта сверяются с заказом, чужие memo игнорируются).
  Приёмка: тест на фикстурах транзакций: точная оплата, недоплатa, чужой memo.
- ☑ **2.3 SlotHashes до оплаты.** При создании заказа бэкенд публикует
  коммитмент сида (как в текущем Verify), сид раскрывается при минте.
  Приёмка: Verify пересчитывает результат по раскрытому сиду (тест).

## Фаза 3. Бэкенд: прямой минт cNFT (без программы)

- ☑ **3.1 Билдер инструкции минта.** Backend строит Bubblegum
  `mintToCollectionV2` напрямую (web3.js + borsh, без chip_core):
  `backend/src/bubblegum-mint.ts` (метаданные из существующих шаблонов
  коллекций, leaf owner = покупатель, delegate = owner).
  Приёмка: юнит-тест раскладки инструкции (дискриминатор, аккаунты, args)
  на фикстурах; devnet-минт — п. 1.4 связкой.
- ☑ **3.2 Очередь минтов (кранк).** Заказы `paid` → минт n фишек заказа →
  `minted` с asset id; ретраи при фейле RPC, защита от двойного минта
  (статус + уникальный order_id в метаданных/журнале).
  Приёмка: тест — повторный прогон кранка не минтит дважды.
- ☑ **3.3 Журнал минтов + Verify.** Публичный журнал (order, asset, seed,
  rarity) и доработка `/verify`: пересчёт по журналу без ончейн-программы.
  Приёмка: API-тест журнала; клиентский Verify показывает запись журнала.

## Фаза 4. Бэкенд: слияние бёрн+минт

- ☑ **4.1 Бёрн-верификация.** Клиент подписывает Bubblegum burn трёх cNFT;
  бэкенд проверяет бёрн-события (индексатор/DAS: владелец, asset id, дерево).
  Приёмка: тест — чужой/уже сожжённый asset отклоняется.
- ☑ **4.2 Результат и кулдауны.** По рецепту `FUSION_RECIPES` (шанс, возврат
  при фейле, комиссия $CG списывается бэкендом с баланса игрока),
  результат минтится п. 3.1; кулдаун результата (1ч/6ч/24ч/48ч/72ч)
  в БД + поле `lockUntil` в API как сейчас.
  Приёмка: тесты таблицы рецептов (шанс/кулдаун/возврат) на бэкенд-пути.

## Фаза 5. Бэкенд: мягкий стейкинг и награды

- ☑ **5.1 Учёт владения.** Начисления стейкинга только пока индексатор
  видит фишку у владельца (проверка по DAS при начислении и клейме).
  Приёмка: тест — проданная фишка перестаёт начислять.
- ☑ **5.2 Выплаты $CG.** Клейм награды переводом с пула казны
  (идемпотентный claim id).
  Приёмка: тест — повторный клейм не платит дважды.
