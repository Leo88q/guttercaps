# Mac → devnet: обновить, собрать, протестировать, задеплоить

Одна команда в Terminal на MacBook: подтягивает свежий код с GitHub, проверяет и при необходимости ставит
инструменты, гоняет тесты, собирает программы **для devnet** и деплоит их в **devnet**.
Сам скрипт: [`scripts/mac-devnet.sh`](../scripts/mac-devnet.sh). Его самотест (обновление из GitHub и защита от
mainnet): `npm run selftest:macdevnet`, входит в `npm run verify`.

> Скрипт работает только с devnet. Он отказывается продолжать, если URL RPC содержит `mainnet`, и — независимо
> от URL — если `solana genesis-hash` ответа RPC не равен genesis-хэшу devnet. Ни одна транзакция до этой
> проверки не отправляется.

## 1. Команда

```bash
cd /Users/zlata/LeoGamesStudio/guttercaps \
  && git fetch origin main \
  && BRANCH=main bash <(git show FETCH_HEAD:scripts/mac-devnet.sh)
```

Как это устроено. `git fetch` приносит ветку с GitHub. `git show FETCH_HEAD:scripts/mac-devnet.sh` берёт скрипт
прямо оттуда — в локальной папке он может ещё не лежать. Первым делом скрипт сам обновляет папку (этап `update`)
и дальше перезапускается **своей свежей копией из репозитория**. Если ветка другая — подставьте её в `git fetch
origin <ветка>` и в `BRANCH=<ветка>`.

Когда папка уже обновлена: `npm run mac:devnet` (то же, что `bash scripts/mac-devnet.sh`).

## 2. Этапы (порядок важен)

| этап | что делает | заметка |
|---|---|---|
| `update` | `git fetch`, fast-forward на `$BRANCH` | правки, которые можно восстановить, сбрасываются, ваши — в `git stash` (см. раздел 5) |
| `doctor` | что установлено, чего не хватает | ничего не меняет |
| `toolchain` | Node 24, Rust 1.89.0, solana CLI 2.1.0 (Agave), Anchor 0.31.1, `npm ci` | перед каждой установкой спрашивает `[y/N]`; версии берутся из `Anchor.toml`, `rust-toolchain.toml`, `.nvmrc` |
| `verify` | `npm run verify` — 28 проверок Node/Python, как в CI | около 3 минут |
| `rust` | `npm run programs:gate` — `cargo fmt --check`, `clippy -D warnings`, `cargo test`; clippy и тесты с `--locked` | как в CI: только `deprecated` / `unexpected_cfgs` из макросов Anchor разрешены; первая компиляция всех зависимостей долгая |
| `localnet` | сборка `--features localnet` + 92 сценария LiteSVM (`npm test`) | нужен `sb_mock` (подставной Switchboard); эти `.so` на devnet никогда не попадают |
| `ids` | ключи программ и `declare_id!` (см. раздел 6) | |
| `build` | сборка `--features devnet` + `verify-deploy artifact --cluster devnet` | `chip_core.so` и `arena.so` обязаны нести пины devnet-Switchboard и не нести ни `sb_mock`, ни mainnet |
| `deploy` | 4 программы в devnet, затем `verify-deploy onchain` | сначала печатается бюджет (залог / пик / комиссии / резерв) и проверяется баланс; программа, байты которой уже лежат в devnet, пропускается; выросшая — сперва `program extend`; буфер загрузки переиспользуется, если его предыдущий запуск уже создал; на выходе: байты в сети == локальный `.so`, upgrade authority == ваш кошелёк |
| `setup` | `npm run setup` (mints, config, коллекции, emission, arena) + lookup table | идемпотентно; адреса mint запоминаются |
| `env` | `client/.env.local` и `backend/.env` под этот деплой | чужие файлы не перезаписываются |
| `pyth` | ключ Pyth API, кошелёк pusher'а, pusher цен в Docker, проверка «свежие SOL/USD и SKR/USD на чейне» | без неё SOL- и SKR-оплата не работает (раздел 7); ключ скрипт спрашивает в начале, на этапе `toolchain` |
| `run` | (по желанию) бэкенд + pusher цен + клиент, откроется браузер | `bash scripts/mac-devnet.sh run` |
| `faucet` | (по желанию) devnet-SOL и стенд-ин SKR кошельку из браузера | `bash scripts/mac-devnet.sh faucet <адрес>` |

Порядок `localnet` → `build` не случаен: тесты запускаются на сборке с `sb_mock`, а деплоится сборка с
настоящим devnet-Switchboard. `build` перезаписывает `target/deploy`, поэтому тесты всегда раньше.
Тесты идут на закоммиченных id программ (как в CI); свои id применяет этап `ids` уже после тестов.

Время: первый прогон — это две сборки Rust/SBF, компиляция host-тестов и загрузка platform-tools; считайте от
получаса до пары часов в зависимости от Mac. Повторные запуски быстрее за счёт кэша cargo.

## 3. Что нужно заранее

* macOS, интернет, свободно ≈15 ГБ (`target/` у Rust большой). Xcode Command Line Tools — если их нет, скрипт
  запустит установку (окно macOS) и попросит запустить команду заново.
* **SOL на devnet.** Деплой 4 программ — это арендный депозит за их размер плюс временный буфер самой большой
  программы, который возвращается. Скрипт спрашивает ставку у самого кластера (`solana rent`, тот же
  `getMinimumBalanceForRentExemption`, что и `solana rent 1000000 --url devnet`) и печатает бюджет четырьмя
  отдельными строками — постоянный залог, временный пик, сетевые комиссии, резерв. По размеру CI-артефактов
  (1 459 024 + 604 272 + 937 320 + 567 632 = 3 568 248 байт) и ставке 5080 лампортов на байт это:

  | строка | сколько | что это |
  |---|---|---|
  | арендный залог | ≈ 18.13 SOL | `Program` + `ProgramData` четырёх программ. Постоянный: вернётся только через `solana program close`, то есть потеряв программу |
  | временный пик | ≈ 7.41 SOL | самый большой буфер загрузки. Буферы идут по очереди и loader обнуляет использованный, поэтому пик — это максимум, а не сумма |
  | сетевые комиссии | ≈ 0.04 SOL | ~4000 транзакций `write` по 900 байт ELF + deploy/extend |
  | резерв | 3.00 SOL | `setup`, lookup table, crank, pusher цен. Не сетевая комиссия: это `MAC_DEVNET_OPS_RESERVE_SOL` |
  | **итого** | **≈ 24.1 SOL** | |

  Итог — это **не** сумма четырёх строк. Скрипт деплоит программы по очереди, а loader возвращает буфер
  сразу после деплоя из него, поэтому живёт ровно один буфер: на шаге *k* нужно «залоги программ 1..k +
  буфер *k* + комиссии 1..k». Самый тугой шаг (последний, `arena`: 18.13 + 2.88 + 0.04 = 21.06 SOL) и есть
  то, на что funded кошелёк; сверху добавляется резерв. Сумма всех строк (28.59 SOL) предполагает четыре
  одновременных буфера, чего в этом цикле не бывает, — она печатается отдельной строкой для сверки, но не
  используется. Консервативность сохранена: переоценка не останавливает деплой, недобор — да.

  Почему раньше нужно было ~38 SOL, а теперь ~24: `solana program deploy` без `--max-len` выделяет
  `ProgramData` **вдвое** больше `.so` («twice the size of the original deployment … room for program
  growth») — на четырёх бинарниках это 36.3 SOL залога вместо 18.1. Теперь скрипт передаёт точную длину
  (`MAC_DEVNET_MAX_LEN_HEADROOM=0` по умолчанию), а выросший бинарник расширяет уже существующей веткой
  `solana program extend`. Ошибиться тут нельзя: бюджет считается из того же числа, которое уйдёт в
  `--max-len`, и `npm run selftest:macdevnet` проверяет это на реальных размерах.
  Ставка не зашита в скрипт: 6960 лампортов/байт (3480 × 2 года) — параметры 2021 года, кластер 2026-го берёт
  5080. Если RPC не ответил, этап останавливается и печатает команду продолжения, а не угадывает число;
  «программа не найдена» и «RPC не ответил» — разные ответы, и скрипт их различает.
  Скрипт сначала пробует `solana airdrop`, а если публичный airdrop ограничен — печатает адрес и ждёт: пополните
  на <https://faucet.solana.com> (сеть Devnet; за один заход выдают немного, заходов может понадобиться несколько)
  и нажимайте Enter — баланс перепроверяется, пока не хватит. Поэтому лучше пополнять заранее: адрес кошелька
  скрипт печатает на этапе `toolchain` (если кошелька ещё нет — предложит создать его там же, чтобы пополнять,
  пока идут тесты и сборка).
* Кошелёк деплоя: `~/.config/solana/id.json` (другой — `WALLET=/путь/к/ключу.json`). Если файла нет, скрипт
  предложит создать новый. Этот же кошелёк — **upgrade authority** программ и админ для `npm run setup`
  (программы принимают `initialize` / `init_arena` только от него).
* Для проверки покупок за USDC нужен devnet-USDC (mint `4zMMC9…`): <https://faucet.circle.com>.
* **Для оплаты SOL и SKR** (раздел 7): ключ Pyth API (<https://pythdata.app/signup>, есть бесплатный пробный период)
  и Docker Desktop (<https://www.docker.com/products/docker-desktop/> или `brew install --cask docker`). Без них всё
  остальное работает, а SOL/SKR-оплата выключена; скрипт скажет об этом прямо.

## 4. Что скрипт меняет на машине

* Глобально, только после вашего `y`: rustup и Rust-toolchain 1.89.0; solana CLI **2.1.0 становится активным**
  (прежнюю версию можно вернуть `agave-install init <версия>`); Anchor 0.31.1 — через `avm`, если он есть, иначе
  готовым бинарником релиза в `~/.cargo/bin` (без 10-минутной компиляции); `node@24` через Homebrew, если Node другой.
* В репозитории: `target/mac-devnet/` (состояние и логи запусков — каждый запуск пишет `run-<время>.log`),
  `client/.env.local`, `backend/.env` (только если их нет или они созданы этим скриптом), правки id программ
  (раздел 6).
* Вне репозитория: `~/.config/solana/guttercaps/` — ключи программ (`programs/`), ключи буферов деплоя
  (`buffers/`), ключ crank (`crank.json`), кошелёк pusher'а (`pyth-payer.json`), ключ Pyth API (`pyth-api-key`).
  Права 0600/0700.
* Docker: контейнер `guttercaps-pyth-pusher` живёт только пока идёт этап `pyth` или сессия `run`; Ctrl+C и выход
  его останавливают (если вдруг остался: `docker rm -f guttercaps-pyth-pusher`).

## 5. Возобновление и частичные запуски

Любой сбой печатает этап и точную команду продолжения. Все этапы идемпотентны.

```bash
bash scripts/mac-devnet.sh --from build        # продолжить с этапа
bash scripts/mac-devnet.sh --only deploy,setup # только эти этапы
bash scripts/mac-devnet.sh --skip rust         # всё, кроме этапа (например, без долгого cargo test)
bash scripts/mac-devnet.sh --yes               # не спрашивать перед установками и созданием кошелька
```

Обновление из GitHub бережёт вашу работу:

* `package-lock.json`, изменённый голым `npm install`, и правки, где поменялись **только публичные ключи** в тех
  13 файлах, которые переписывает `program-ids apply`, — сбрасываются (их нечем потерять: всё воспроизводится);
* любые другие незакоммиченные правки уходят в `git stash` (`git stash list` → `git stash pop`);
* ваши незапушенные коммиты остаются на месте; если локальная ветка разошлась с GitHub, старая версия
  сохраняется в ветке `backup/before-update-<время>`, а ветка переключается на GitHub-версию;
* неотслеживаемые файлы не трогаются.

Берегите `~/.config/solana/guttercaps/programs/`: без этих ключей нельзя создать программы по тем же адресам
(обновлять существующие можно и с кошельком-authority). Если у вас есть ключи под заглушки — `PROGRAM_KEYS_DIR=DIR`.
Другие ключи = другие адреса = новые программы; прежние останутся на devnet.

## 7. Запуск приложения и оплата SOL / SKR

```bash
bash scripts/mac-devnet.sh run
```

Поднимает бэкенд (API + индексатор + crank + кэш цен; лог — `target/mac-devnet/logs/backend.log`), **pusher цен
Pyth** (лог — `target/mac-devnet/logs/pyth-pusher.log`) и dev-сервер клиента на <http://localhost:5173>; Ctrl+C
останавливает всё. В кошельке браузера (Phantom / Solflare) переключите сеть на **Devnet**. Crank подписывает
reveal/открытие паков, ему нужно ≈1 SOL: этап `env` переводит его с кошелька деплоя, если там достаточно.

### Зачем нужен pusher и что для него нужно

Программа `chip_core` пересчитывает оплату SOL и SKR в доллары по цене Pyth из аккаунта `PriceUpdateV2`, который
не старше 60 секунд, а цену SKR/USD никто, кроме нас, не публикует (это не «спонсируемый» фид). Поэтому студия
запускает официальный `price_pusher` Pyth (`ops/pyth-pusher/`). Без него покупки за USDC и $CG работают, а магазин
сам прячет SOL и SKR.

Что нужно и что делает скрипт:

* **Ключ Pyth API.** С 26.08.2026 любой запрос к Hermes (источнику цен Pyth) требует ключ:
  <https://pythdata.app/signup>, есть бесплатный пробный период (по его окончании нужен платный план). Скрипт
  спрашивает ключ один раз в начале (ввод скрыт), тут же проверяет его у Hermes (и что SOL/USD и SKR/USD
  отдаются) и сохраняет в `~/.config/solana/guttercaps/pyth-api-key` (права 0600). Можно и так:
  `PYTH_API_KEY=… bash scripts/mac-devnet.sh`. Ключ нигде не печатается: ни в логах скрипта, ни в логе pusher'а.
  Единственное место, где он виден, — параметры контейнера (`docker inspect`) на вашем Mac, пока контейнер жив:
  это ключ пробного периода, при необходимости его перевыпускают на <https://pythdata.app>. Enter вместо ключа —
  пропустить.
* **Docker.** pusher — официальный образ `xc-price-pusher` (версия берётся из `ops/pyth-pusher/.env.example`,
  нужна ≥ v10.5.0: в ней появился `--hermes-access-token`; прежняя v9.3.0 ключ передать не могла). Установлен, но
  не запущен Docker Desktop скрипт откроет сам. npm-пакет pusher'а не годится: он не стартует на свежей установке.
* **Кошелёк pusher'а** `pyth-payer.json`: скрипт создаёт его и переводит 1 SOL с кошелька деплоя (публикация
  цен ≈ 0,07 SOL в сутки, пока pusher работает, плюс два аккаунта по ≈ 0,002 SOL).
* **Этап `pyth`** запускает pusher и ждёт, пока `npm run pyth-pusher -- check` подтвердит, что обе цены в devnet
  свежие, печатает цены и во сколько SOL и SKR обойдётся пак за $4,99, предупреждает, если доверительный интервал
  цены шире 2 % (программа откажет в такой оплате), и останавливает pusher: дальше он запускается вместе с `run`.

### Тестовые SOL и SKR для кошелька из браузера

Чтобы заплатить SOL, кошельку нужен devnet-SOL, а чтобы заплатить SKR — стенд-ин SKR (его минт создал `setup`,
и управляет им кошелёк деплоя; настоящий SKR выдать нельзя). Одна команда даёт и то и другое:

```bash
bash scripts/mac-devnet.sh faucet <адрес кошелька из браузера>            # 2 SOL + 1000 SKR
bash scripts/mac-devnet.sh faucet <адрес> --sol 1 --skr 50000             # свои суммы
```

USDC берётся на <https://faucet.circle.com> (Solana Devnet). $CG выдаёт сама игра: отдельного faucet у него нет.

### Арена: подготовка большой транзакции

Для боя нужны **три фишки с общей силой не ниже 400**; фишки в стейкинге тоже подходят.
Создание и принятие боя на $CG несут три Bubblegum V2 proof. Если пакет не помещается в 1232 байта,
клиент сначала создаёт/дополняет многоразовую таблицу адресов (ALT) под управлением игрового кошелька.
Кошелёк запросит дополнительные подтверждения; нужны devnet-SOL на комиссии и rent таблицы. **Ставка
$CG отправляется только в последней транзакции**, вместе с инициализацией randomness; подготовка ALT
сама по себе не создаёт бой. После подготовки proofs читаются заново, и клиент ждёт активации новых
адресов в следующем слоте.

Адреса этих таблиц сохраняются в localStorage под префиксом `gc.arena.lookup-tables:` (отдельно для
RPC и кошелька). Повторная попытка использует сохранённую таблицу. Очистка данных браузера **не**
возвращает rent: таблица остаётся на чейне. Для возврата депозита владелец может деактивировать её и,
после предусмотренной Solana задержки, закрыть через инструменты управления ALT; больше не используйте
закрываемую таблицу для новых боёв.

Fallback без DAS восстанавливает proof из текущего changelog, правой ветви и canopy дерева и обязательно
проверяет его против корня. Это не бесконечный индексатор: если нужные узлы уже вытеснены из истории,
нужен devnet RPC с DAS в `VITE_DAS_RPC_URL` в `client/.env.local`, затем перезапуск клиента. Нельзя
лечить такой случай пропуском проверки proof.

Если после отправки стейка/боя подтверждение истекло, клиент сверяет статус подписи, а не отправляет
деньги повторно вслепую. При сообщении «Транзакция отправлена, но подтверждение не получено» сначала
откройте ссылку на транзакцию и проверьте баланс/позицию. Для диагностики раскройте «Технические
подробности»: одно общее сообщение об истечении срока не показывает, где именно произошла ошибка.

**Отдельный случай — `Transaction simulation failed: Blockhash not found`.** Это явный отказ
RPC на preflight, а не неизвестное подтверждение. Клиент получает blockhash вместе с контекстом слота
и передаёт `minContextSlot` при отправке, чтобы отстающий узел балансировщика не проверял его на более
старом состоянии. При таком ответе SDK и включённом preflight клиент один раз получает новый blockhash
и просит новую подпись. Повторный отказ показывает `blockhash_rejected`, без ссылки на якобы ожидающий
платёж; детали содержат слот, оба blockhash и время от получения blockhash до отказа. Тайм-аут сети,
истечение подтверждения и простой текст `Blockhash not found` без явного отказа симуляции **не** разрешают
такой повтор. Не отключайте preflight ради обхода ошибки. Если отказ сохраняется, проверьте devnet RPC
и время подтверждения в кошельке, не меняя ключи/ID программ и не повторяя деплой.

**Первый стейк $CG и `AccountNotInitialized [3012]`.** В старом setup отсутствовал
`vault_cg` — ATA монеты $CG с владельцем `emission` PDA программы staking. `init_emission`
создаёт пулы, но не этот токеновый счёт. Исправленный клиент включает idempotent-создание
ATA игрока и хранилища перед `stake_cg` **в одну транзакцию**. Для уже запущенной игры
достаточно обновить клиент; повторять init/deploy не нужно. Если хранилища ещё нет, его rent
оплачивает первый стейкер в SOL. Если оно есть, ATA-инструкция не создаёт второй счёт.
Новый setup также создаёт хранилище на этапе `atas`. Это не универсальное лечение `3012`:
если лог называет другой аккаунт (например, `emission` или `pool`), нужна отдельная проверка
настройки — клиент не инициализирует администраторские пулы от имени игрока.

### DAS и ошибки Switchboard в консоли

- DAS — отдельные JSON-RPC методы, а не обычный `getAccountInfo`. `getAsset` и `getAssetProof`
  отправляются с `params: { "id": "…" }`; `getAssetsByOwner` — с `ownerAddress`, `page`, `limit`
  и `displayOptions` в объекте параметров (как в официальном Helius SDK). Массивы с вложенными
  опциями не соответствуют этому контракту. Формат исправлен и в клиенте, и в backend/crank.
- Если `VITE_DAS_RPC_URL` не задан, DAS следует за RPC, выбранным в профиле. Явно заданный
  `VITE_DAS_RPC_URL` имеет приоритет: это должен быть endpoint **той же сети Devnet**, поддерживающий
  Bubblegum V2 DAS. `METAPLEX_DAS_RPC_URL` настраивает backend отдельно; выбор RPC в браузере
  не меняет backend. Обычный публичный Solana RPC не становится DAS-сервисом от смены URL-переменной.
- При смене RPC в профиле клиент больше не переносит на него старый `VITE_RPC_WS_URL`: web3.js
  выводит WS из нового HTTP-адреса. Это устраняет смешивание провайдеров, но не лечит отказ
  провайдера, DNS или неработающий/отозванный API-ключ.
- `Merkle proof history is no longer available` означает, что локальное восстановление из
  дерева невозможно. Теперь `proof_unavailable` сохраняет **обе** ошибки в технических подробностях:
  `details.das` (например, HTTP 401, метод не поддерживается, неверные параметры) и `details.tree`.
  Нельзя отключать проверку proof или заменять отсутствующие узлы нулями.
- `ERR_NAME_NOT_RESOLVED` у Crossbar и CORS у gateway — отдельные сетевые ошибки. В используемом
  SDK выбор оракула допускает проверенный on-chain fallback, поэтому ошибки health-запросов
  сами по себе не доказывают остановку создания боя. Для reveal всё равно нужна доступная служба
  оракула; исправление DAS не делает недоступный gateway рабочим. Не отключайте защиту браузера.
- `buffer.Buffer` больше не должен подменяться Vite browser-external заглушкой: `buffer` и
  `node:buffer` явно направлены на установленную браузерную реализацию. После обновления полностью
  перезапустите Vite. Не публикуйте URL RPC с `api-key` в скриншотах/логах; показанный ключ перевыпустите.

**`CreateLookupTable: … is not a recent slot`.** Слот находится внутри инструкции и участвует
в выводе адреса ALT — обновление одного blockhash не исправляет его. Арена теперь выбирает слот
из подтверждённого `SlotHashes`, а не вычисляет `getSlot() - offset` (пропущенные слоты могут
вообще не входить в историю). Контекст этого чтения передаётся в получение blockhash и preflight
через `minContextSlot`; для готовых ALT учитывается также слот активации адресов. Если кошелёк
был открыт долго и RPC явно отклонил create на симуляции, клиент один раз заново читает историю
и пересобирает **инструкцию и адрес** таблицы. Для атомарного init randomness + бой аналогично
обновляются слот и proofs, максимум одна повторная попытка после такого отказа. Сетевой тайм-аут,
неизвестное подтверждение и отказ пользователя **не** разрешают этот повтор. Предыдущие адреса
таблиц остаются в реестре для восстановления после неоднозначного результата; очищать localStorage
или закрывать таблицы для этого исправления не нужно. Это не устраняет недоступность Switchboard.

### Проверка blockhash без новых платежей

Если `blockhash_rejected` сохраняется, не проверяйте гипотезы новыми ставками. Откройте `/profile`,
в настройках рядом с RPC нажмите **«Проверить RPC (без платежа)»**. Проверка не запускается сама,
не вызывает кошелёк, `simulateTransaction` или `sendTransaction`. Она использует **активный RPC
соединения браузера**, а не только значение `.env` и не несохранённый текст в поле настройки.

Запрашиваются genesis hash, свежие confirmed/finalized blockhash, `isBlockhashValid` и высота блока.
Те же hash проверяются сразу и после паузы 45 секунд (сетевые задержки увеличивают общее время).
Для обеих проверок валидности используется commitment `confirmed`; отсутствие только что полученного
confirmed hash в finalized bank не выдаётся за неисправность. В отчёте есть `remainingBlocks`,
контексты слотов и длительности RPC. Отрицательный остаток означает превышение `lastValidBlockHeight`
в момент чтения высоты; невалидный hash при положительном остатке требует отдельного анализа RPC/ветки.
Совпадение `blockhash` и `signedBlockhash` в ошибке исключает их замену кошельком в этой попытке,
но время `signingElapsedMs` включает также отправку и получение отказа — это не только время пользователя.

Скачайте `guttercaps-rpc-check.json` кнопкой под отчётом. В JSON нет URL, API-ключа, адреса кошелька
или произвольного текста ошибок провайдера; endpoint обозначается коротким SHA-256 отпечатком.
Сетевые ошибки представлены кодами HTTP/RPC, без сырых тел ответов. Можно отменить проверку;
смена RPC и уход со страницы отменяют её. Это диагностика, не доказательство успешной игры и
не проверка доступности Switchboard. В демо-режиме кнопка отключена.

### Switchboard: серверный доступ вместо браузерного CORS

Выбор оракула и HTTP reveal больше не идут из браузера на Crossbar / внешний gateway.
Клиент использует `/v1/switchboard/health` и `/v1/switchboard/reveal/<randomness>` через обычный
Vite/nginx API proxy. Backend читает закреплённую очередь, проверяет владельцев аккаунтов,
heartbeat и срок SGX verification. Для live-health используется серверный discovery из SDK:
`https://crossbar.switchboard.xyz/gateways?network=devnet` (mainnet — соответствующий параметр).
Его ответы объединяются с gateway URI участников on-chain очереди. Crossbar не обязателен:
при его отказе остаются адреса из блокчейна. Ответы `healthy_oracles` объединяются по публичному
ключу оракула, как в `Queue.inspectRandomnessOracles` SDK. Gateway может сообщать о другом оракуле;
его собственный владелец не обязан быть eligible, но **выбранный** oracle обязан пройти все on-chain проверки.
Проверяются только HTTPS-адреса без credentials/query/fragment, с публичным DNS и без redirect.
Лимиты: до 16 адресов из каждого источника, 8 параллельных запросов, 8 секунд на запрос.
Если ни один оракул не прошёл проверку, `prepareRandomness` останавливает создание покупки/ставки
до инициализации и подписи. On-chain-only fallback при недоступном gateway больше не используется.
Слот для init читается из SlotHashes после проверки доступности, а не до сетевого ожидания.

После обновления перезапустите **backend и client** (`Ctrl+C`, затем
`bash scripts/mac-devnet.sh --no-update run`). Программы redeploy не требуют, `.env` перегенерировать
не нужно. Без кошелька и без ставки откройте:

```text
http://localhost:5173/v1/switchboard/health
```

- `ready: true`: выбран оракул, доступный **в момент проверки**, с действительными on-chain данными.
- `ready: false`: новая операция заблокирована. `probes` покажет доступность каждого проверенного
  eligible oracle; `healthGateway` укажет источник live-health, `directCode` — результат собственного
  endpoint. `discovery` показывает состояние реестра, `gatewayChecks` — ответы всех проверенных gateway.
  `gateway_http_502` означает ответ внешнего gateway, `gateway_dns` — DNS backend,
  `gateway_timeout` — таймаут 8 секунд, `oracle_not_live` — нужного оракула нет в живом пуле gateway.
- `switchboard_cluster_mismatch`: backend RPC не соответствует закреплённому Switchboard program;
  `switchboard_rpc_unavailable`: не удалось прочитать RPC/IDL; `unsafe_gateway`: URI/DNS не прошёл защиту.
- `404` / HTML вместо JSON: запущен старый backend или не работает `/v1` proxy.

JSON не содержит RPC URL, API-ключей и сырых ошибок внешних сервисов. Проверка single-flight,
кэш 5 секунд, лимит 12 запросов/мин/IP; браузеру ответ отдаётся с `no-store`. Повторять каждую
секунду не нужно. Клиент не использует mock-ответы для этого допуска к реальной операции.

Reveal endpoint принимает **только публичный ключ committed randomness account**. Сервер сам читает
seed/slot/oracle и использует публичный RPC кластера, не пересылая приватный RPC ключ внешнему сервису.
Он не подписывает и не отправляет транзакции. Подпись/значение oracle остаются неизменными и проверяются
Switchboard при исполнении on chain. Переключать oracle после commit нельзя. HTTPS transport запрещает
redirects, локальные/служебные DNS адреса (включая DNS rebinding), credentials/query/fragment в URL
и слишком большие ответы. URI из проверенного on-chain oracle account — **базовый URL**, который может
содержать путь. Этот префикс сохраняется: к нему добавляется `/gateway/api/v1/healthy_oracles` или
`/gateway/api/v1/randomness_reveal`, как в SDK и crank. Путь не принимается из HTTP-запроса пользователя.
Завершающие `/` убираются перед добавлением суффикса; путь не отбрасывается при приведении к origin.
В JSON health по-прежнему выводится только origin, без пути. Отказ `unsafe_gateway` у HTTPS-адресов
с корректными DNS именами и префиксом пути в первой версии relay был ошибкой нашего URL-фильтра,
а не доказательством недоступности Switchboard. После обновления повторите только read-only health.

Если `gateway_timeout` сохраняется, но `curl` к **корню** gateway быстро получает HTTP 200, это ещё
не проверка API-маршрута. Из корня репозитория выполните `npm run switchboard:doctor`.
Это отдельный read-only процесс: сам читает `backend/.env`, не требует остановки приложения,
не загружает кошелёк/БД и не создаёт транзакции. Для максимум двух eligible gateway он сравнит
**одинаковый полный URL** `healthy_oracles` нашим Node transport и `curl`, сохранив on-chain префикс.
В JSON выводятся публичные oracle origin/path, этапы Node (`dns_start`, `dns_done`, `tcp`, `tls`,
`headers`, `body`, `error`) и timings curl. Для сетевой ошибки допускается только фиксированный
системный/TLS код, без исходного текста исключения. Curl также показывает версию HTTP и признак
ожидаемого JSON-массива `oracles`, не копируя само тело ответа. RPC URL/ключи, содержимое ответов и сырые исключения не выводятся.
Таймаут Node остаётся 8 с; curl — 12 с, плюс DNS до 5 с. Curl работает без proxy/curlrc,
с TLS-проверкой, без redirect и с привязкой к проверенному публичному IPv4; `resolveMs` — время
отдельного DNS lookup, а `curl.dnsMs` отражает уже закреплённый адрес. User-Agent/сетевые реализации
различаются, поэтому совпадение URL не означает побайтово одинаковые запросы. Doctor не меняет
боевые таймауты и не доказывает готовность reveal/settlement. Полный JSON можно передать для разбора.

Независимая проверка сети (2026-10-08 22:52 UTC / 2026-10-09 01:52 MSK):
[GitHub-hosted control run](https://github.com/Leo88q/guttercaps/actions/runs/37856168845)
получил полный `healthy_oracles` JSON по тем же `/devnet/gateway/api/v1/healthy_oracles`
адресам `141.95.35.110.xip.switchboard-oracles.xyz` и `141.95.98.113.xip.switchboard-oracles.xyz`:
HTTP 200, 32 304 байта, 5 записей, примерно 0,65 секунды. С Mac эти URL ранее
не завершили передачу за 8/12 секунд. Crossbar DNS не разрешился и на runner.
Это измерение доступности HTTP с другой сети, **не** подтверждение eligibility, reveal или settlement.
Оно не определяет конкретную причину различия (провайдер, фильтрация, VPN, MTU или локальная настройка).

При таком различии проверяйте **системный** VPN/full tunnel с DNS либо другую сеть выхода
для backend, не браузерное расширение. Встроенный HTTPS transport не использует обычные
`HTTP_PROXY`/`HTTPS_PROXY` как настройку прокси; curl doctor явно отключает HTTP-прокси.
Full tunnel действует на сетевой маршрут и не требует отключения проверки TLS.
После изменения маршрута подождите истечения 5-секундного health cache и прочитайте
`/v1/switchboard/health` без новой ставки. Если backend расположен на другом хосте,
менять нужно его выход в интернет, а не только сеть браузера.

Workflow `switchboard-network.yml` — отдельный read-only контроль публичных фиксированных URL,
не часть readiness приложения. Не читает `.env`, не использует RPC, кошельки или секреты,
не отправляет транзакций. Автоматически запускается только при изменении его файлов на текущей
диагностической ветке; расписания нет. `scripts/switchboard-network.py` выводит только размеры,
классификацию Content-Type, JSON shape и тайминги, но не тела ответов. Успешный job означает
полный health-ответ хотя бы одного endpoint, **не** готовность к ставке.

Это устраняет **браузерную** зависимость от CORS и прямых запросов Crossbar, но не чинит выключенный внешний oracle.
При общей недоступности gateway новые операции блокируются, уже оплаченные нельзя создавать повторно:
они продолжаются штатным resume/crank после восстановления (либо штатным refund, если применимо).
Важно: серверный discovery меняет только выбор/проверку live-health, **не** reveal URL.
Reveal и crank продолжают использовать URI закоммиченного oracle, как `Randomness.revealIx` SDK.
Работоспособность `healthy_oracles` через агрегатор не доказывает доступность `randomness_reveal`;
никакой автоматической ставки или переключения committed oracle эта проверка не запускает.
Существующий crank уже обращается к gateway на сервере; ошибки DNS/502 могут затрагивать и его.
`ready: true` не доказывает успешное settlement: для ставок дополнительно нужен запущенный и правильно
настроенный `battle` worker (`WORKERS`, `BATTLE_ORACLE_KEYPAIR`).

### Запуск обработчика боёв на Mac Devnet

`mac-devnet.sh run` теперь выбирает `crank,pyth,battle`, **если `WORKERS` не задан**.
Глобальный default backend вне этого Mac-скрипта остаётся `crank,pyth`.
Явный `WORKERS` из окружения/backend `.env` сохраняется, включая пустой список.
Если в нём нет `battle`, запуск явно предупреждает, что автоматического завершения боёв не будет.

Перед запуском backend выполняется `scripts/mac-battle-preflight.mts`:
- читает genesis и требует Devnet;
- проверяет owner/discriminator `ArenaConfig`, совпадение `battle_oracle` с выбранным ключом и отсутствие pause;
- требует стартовый запас **0.001 devnet SOL** у подписанта (не гарантия средств на все будущие транзакции);
- ничего не подписывает, не пополняет кошельки, не меняет конфигурацию в блокчейне и не открывает DB.

Выбор ключа: явный `BATTLE_ORACLE_KEYPAIR`, иначе `$WALLET` Mac-скрипта **только как кандидат**.
Deployer допускается лишь после совпадения его публичного ключа с on-chain `battle_oracle`.
Это локальное Devnet-удобство; для production нужен отдельный resolver key.
`battle_oracle_mismatch` выводит только ожидаемый и фактический публичные ключи: укажите файл
уже назначенного oracle, не меняйте `ArenaConfig` на случайный новый ключ.
`battle_fee_reserve_low` требует пополнения **правильного** подписанта тестовым SOL;
`battle_arena_paused` / `battle_config_missing` / `battle_config_owner` / `battle_requires_devnet`
останавливают запуск до устранения причины. Сырые RPC errors, ключи и полный `.env` не публикуйте.
Проверка использует тот же backend `.env`, что и сам процесс; файл не переписывается,
его секреты не экспортируются в окружение Vite.

При ошибке проверки новый backend не запускается. Для осознанного режима без арены можно явно
задать `WORKERS=crank,pyth`. Сам battle resolver также больше не подставляет `CRANK_KEYPAIR`,
если забыли `BATTLE_ORACLE_KEYPAIR`.

**Важно:** read-only только предварительная проверка. После успешного старта worker подписывает
Devnet `resolve_battle` для уже принятых подходящих боёв; новые ставки он не создаёт.
В `target/mac-devnet/logs/backend.log` должны появиться `main: started` с `workers=crank,pyth,battle`
и строка `[battle-resolver] oracle …`. Это подтверждение запуска, не доказательство успешного settlement.
Для завершения боя всё ещё нужны reveal, проиндексированные squads и все проверки on-chain.
Деплой программ и повторный setup для этого изменения не нужны.

## 8. Если что-то пошло не так

| симптом | что делать |
|---|---|
| `toolchain '1.89.0' is not installed` | `rustup toolchain install 1.89.0`, затем `--from rust` |
| `rust` падает на `unexpected_cfgs` / `deprecated` из `#[program]` | обновите репозиторий: `programs:gate` должен использовать те же два исключения, что CI (`-D warnings -A deprecated -A unexpected_cfgs`), затем `--from rust`. Остальные предупреждения по-прежнему считаются ошибками |
| в конце лога только `non-local impl definition` / `mpl-core (lib) generated 12 warnings` | это предупреждения старого derive-макроса зависимости, не причина остановки. Ищите первую строку `error:` / `error[E…]:` выше в логе; не обновляйте `Cargo.lock` и не пропускайте `rust` только из-за этого warning |
| `Failed to list installed solana versions` при сборке | `scripts/anchor-build-localnet.sh` чинит это сам; если остаётся — `solana --version` должен быть **2.1.0** (`which -a solana`), см. `tests/localnet/README.md` |
| `Max retries exceeded` / `Blockhash expired` / `write transactions failed` при деплое | публичный devnet теряет транзакции. Повторите `--from deploy` — загрузка продолжится с сохранённого буфера, SOL не пропадают. Помогает свой devnet RPC: `DEVNET_RPC_URL=https://… bash scripts/mac-devnet.sh --from deploy` |
| `insufficient funds` / «не хватает SOL» | пополните кошелёк на <https://faucet.solana.com> (Devnet) и `--from deploy` |
| брошенные буферы держат SOL | `solana program show --buffers -u devnet -k ~/.config/solana/id.json`, затем `solana program close --buffers …` |
| «уже задеплоен с другим upgrade authority» | программа по этому адресу принадлежит другому кошельку: возьмите его (`WALLET=…`) или новые ключи программ |
| `SEC-F7 upgrade-authority pre-flight FAILED` в `setup` | `setup` нужно запускать тем же кошельком, что деплоил (`WALLET`) |
| «выполнено N тестов, ожидалось >= 92» | набор localnet отработал не целиком (пропуски ≠ успех); смотрите лог этапа `localnet` |
| «Hermes отклонил ключ» / pusher пишет 401 | ключ скопирован не целиком или закончился пробный период: <https://pythdata.app>; новый ключ — `bash scripts/mac-devnet.sh --only pyth` (спросит снова) |
| «нет работающего Docker» | установите и запустите Docker Desktop (или `brew install --cask docker`, затем откройте приложение один раз), потом `bash scripts/mac-devnet.sh --only pyth` |
| цены Pyth не появляются (этап `pyth`) | скрипт печатает лог pusher'а. Чаще всего: ключ (401), нет SOL у `pyth-payer.json`, публичный devnet RPC теряет транзакции (`DEVNET_RPC_URL=…`). Живые цены на чейне: `npm run pyth-pusher -- check https://api.devnet.solana.com` |
| «доверительный интервал > 2 %» | цена Pyth слишком «размыта», программа откажет в оплате этой валютой; обычно проходит через несколько минут (SKR — тонкий рынок) |
| хочется всё начать заново | `rm -rf target/mac-devnet` (состояние), при желании — ключи в `~/.config/solana/guttercaps`; новые ключи дадут новые адреса |

Лог каждого запуска: `target/mac-devnet/logs/run-<время>.log` — его достаточно приложить к сообщению об ошибке.

## 9. Чего скрипт не делает

* Не трогает mainnet и не умеет его включать.
* Не делает `npm run skr-pool -- init` (призовой пул SKR; нужен только для проверки SKR-**наград**, а не
  SKR-оплаты: `SKR_MINT=<mint из setup> STAKING_PROGRAM_ID=<id staking> npm run skr-pool -- init`).
* Не оставляет pusher цен работающим после себя: он живёт только пока идёт `pyth` или `run`. Продакшен-вариант
  (две реплики, метрики, алерты) — `ops/pyth-pusher/`.
* Не гоняет браузерные e2e (`npm run e2e:install && npm run e2e:mock` — это mock-сборка, к devnet не относится).
