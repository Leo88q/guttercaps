# Слой данных: что выбрать перед деплоем, и чего это стоит

Документ нужен один раз: `docs/09` §4.1 формулирует вилку «SQLite на одном инстансе vs Postgres-адаптер», и
обе ветки честны. Здесь — измеренные числа вместо оценки «≈3–5 дней», чтобы выбор делался по факту, а не по
ощущению. Дата замеров: 2026-09-17, `backend/src` = 46 файлов, из них 24 содержат SQL.

## 1. Форма того, что есть

Весь доступ к базе идёт через один класс `Db` (`backend/src/db.ts:641`): `run` / `get` / `all` / `scalar` /
`tx`, **синхронные**, с кэшем prepared-выражений. Это единственная граница, и она держится:

| метрика | значение |
|---|---|
| вызовов `db.run/get/all/scalar/tx` | 241 в 21 файле (больше всех — `projections.ts`: 52, `arena.ts`: 32, `reward-oracle.ts`: 31) |
| позиционных биндов `?` | 245 |
| таблиц в DDL | 49 (`db.ts` + `burn-oracle.ts`, у которого своя курсорная таблица) |
| индексов | 39 + 1 частичный |
| «миграция» | не миграции, а `PRAGMA table_info(...)` + `ALTER TABLE ADD COLUMN` на старте (6 таблиц) |

То есть SQL не размазан по слоям и не спрятан в ORM — он лежит в тех же модулях, что и бизнес-логика, и
переносится вместе с ней.

## 2. Измеренный инвентарь диалекта

`docs/09` §4.1 говорил «34 SQLite-специфичных места». Прогнано по исходникам (`grep -o` по `backend/src`),
фактически:

| конструкция | мест | где | чем становится в Postgres |
|---|---|---|---|
| `INSERT OR IGNORE` | 30 | `projections.ts` 22, `arena.ts` 4, `battle-resolver.ts`, `burn-oracle.ts` | `INSERT … ON CONFLICT DO NOTHING` (идемпотентность событий — фундамент индекатора, менять механически и с тестом на каждый файл) |
| `ON CONFLICT … DO UPDATE` | 21 | `projections.ts` 9, `human.ts`, `ingest.ts`, `services.ts` | почти 1:1; различаются `excluded`-нюансы и `RETURNING` (в SQLite его нет вовсе — мест 0) |
| `PRAGMA` | 10 | `db.ts` 9, `finality.ts` 1 | `journal_mode/busy_timeout/synchronous` → настройки сервера; `table_info` → `information_schema.columns` либо настоящие миграции |
| `COLLATE NOCASE` | 7 | `services.ts` 4, `db.ts` 3 | `citext` или `LOWER()` + выражения в индексах (handles: регистронезависимость — часть контракта uniqueness) |
| `json_extract(` | 9 | `queries.ts` 6, `antifraud.ts` 3 | `->>`/`jsonb_path_query`; заодно TEXT-колонки с JSON становятся `jsonb` с GIN |
| `AUTOINCREMENT` | 4 | `db.ts` | `BIGSERIAL`/`IDENTITY` (внимание: `events_raw.id` — порядок replay, `ORDER BY slot, id`) |
| `strftime`, `json_valid`, `RETURNING`, `WITHOUT ROWID`, `fts5` | 0 | — | диалект не въелся туда, куда обычно въедается; поиск по `data LIKE '%' \|\| ? \|\| '%'` (`queries.ts::walletEvents`) — это отдельный разговор: в Postgres просится `pg_trgm`/`tsvector`, и это **улучшение**, а не перенос. Аргумент этого `LIKE` теперь собирается `likePattern` и клауза объявляет `ESCAPE` (SEC-B36): значение из сети не должно уметь писать в паттерн — до фикса `GET /v1/wallet/%/events` отдавал весь лог |
| **итого мест, где SQL диалектен** | **77** | | |

77 правок — это день-два с учётом тестов. Не они определяют цену.

**Статус шва (2026-09-17): строки запросов больше не содержат диалекта.** Все 44 места, где диалект был
написан внутри SQL, собираются через `backend/src/sql.ts` (`insertIgnore` ×30, `insertIfAbsent`, `upsert` ×7,
`foldEq` ×4, `jsonAt`/`jsonFlagEq` ×5), и `backend/test/sql.test.ts` сканирует `backend/src/**` на
`INSERT OR IGNORE`, `INSERT OR REPLACE`, `COLLATE NOCASE`, `json_extract(`, `strftime(`/`ifnull(` — файл с
такой строкой в исполняемом тексте падает тестом. Разрешение на исключение — два файла со *схемой*
(`db.ts`, `burn-oracle.ts`), и оно зафиксировано ассертом, чтобы список не рос молча.

Что этот шов **не** закрывает, и закрыться самими запросами не может:

| осталось | мест | почему это не «поправить SQL» |
|---|---|---|
| DDL-диалект в `db.ts` (`COLLATE NOCASE` ×3, `AUTOINCREMENT` ×4) | 7 | колонки и их collation — это миграция (`prisma migrate deploy`), не текст запроса; на Postgres — `citext`/выражения в индексах и `generated always as identity` |
| `PRAGMA` (`db.ts` 9, `finality.ts` 1) | 10 | режимы WAL/busy_timeout/synchronous живут в конфиге сервера; `table_info` — это `information_schema` либо настоящие миграции |
| seed-строка в DDL-блоке `burn-oracle.ts` | 1 | multi-statement `exec` вместе с остальным DDL |
| плейсхолдеры `?` → `$n` и sync → async | 241 вызов `db.*` в 21 файле | один слой адаптера (`prep/run/all/get/scalar/tx`); именно он, а не SQL, и есть цена перехода |

## 3. Настоящая цена порта: sync → async

`node:sqlite` синхронный, `pg` — нет. Значит каждый из 241 вызова получает `await`, а вместе с ним —
асинхронные функции там, где сейчас обычные (`applyEvents()`, `runCrankTick()`, все `projections`), и
`db.tx(fn)` должен стать транзакцией с `BEGIN/COMMIT` на соединении из пула вместо «мы же синхронные, нас
никто не переключит». Это задевает:

* **индексатор** — идемпотентная пачка «вставил события + применил проекции» должна остаться одной
  транзакцией, иначе переживший crash слот даёт половину состояния;
* **crank** — `crank_jobs` phase-transition под строкой-защелкой (`SELECT … FOR UPDATE` вместо «у нас один
  writer, гонки нет»);
* **тесты** — `backend/test/api.test.ts` и компания живут на `:memory:`; с `pg` им нужен контейнер
  (testcontainers или сервис в CI), и это ровно тот момент, где «477 тестов за 35 секунд» превращается в
  «полторы минуты и docker в CI».

Оценка «3–5 дней» из `docs/09` §4.1 относится к этому, а не к SQL-текстам. Плюс 3–4 дня на миграцию данных и двойную
запись на переходе, если база к тому моменту будет не пустая.

## 4. Вариант A — SQLite + LVM-диск (что мы реально теряем)

Инструменты уже в репозитории, и они определяют RPO/RTO лучше любых обещаний:

* `ops/backup/sqlite-backup.sh` — `sqlite3 .backup` (консистентно под нагрузкой, в отличие от `cp` базы с WAL)
  + `PRAGMA integrity_check` на копии + `KEEP=72` часовых снимков на хосте + опциональный `BACKUP_S3_URI`;
  статус-файл рядом со снимками (`last_success_ts`, `consecutive_failures`, `last_result`) читает API и
  превращает в `backup_*` гейджи, а `alerts.yml` — в `BackupStale`/`BackupFailing` (SEC-B49).
  ⇒ **RPO ≤ 1 час**, и копия, которая точно открывается — но обещание держится только пока снимки
  действительно снимаются: до SEC-B49 отказ бэкапа жил строкой в `docker logs backup`, то есть RPO мог быть
  «сколько угодно» без единого сигнала;
* read-model восстанавливается из цепи: `npm run backend:rebuild` пересобирает проекции из `events_raw`
  ⇒ для игрового состояния (фишки, паки, стейки, наградные руты) **RPO фактически 0** — важна только сама
  цепь и `indexer_cursor`;
* что при откате на почасовой снимок всё-таки теряется: `sessions`/`siws_nonces` (≈ до 1 часа авторизаций —
  пользователи перезалогинятся), `crank_jobs` прогресс (оракул-джобы уходят в `pending`, crank их подберёт;
  риск — только `abandoned`, для которого уже стоит алерт и гейт `/readyz`), `handle_reservations`,
  `analytics_events`, счётчики квестов за последний час.

Ограничение варианта — **один писатель** (`PRAGMA busy_timeout = 5000`, и это осознанный выбор, см. комментарий
в `db.ts`). Реплика на чтение возможна, но `/me`, auth и квесты пишут, так что масштабировать ею можно только
публичные чтения (`/stats`, `/leaderboard`, `/market/listings`) — и только если не побояться лага реплики.

## 5. Вариант B — Postgres: порядок, при котором цена известна

1. `prisma migrate` как источник DDL: сейчас `backend/prisma/schema.prisma` — описание цели без клиента, и
   `npm run schema:check` держит его в синхроне с тем, что реально исполняется (72 задокументированных
   расхождения — это и есть список работ, у каждой строки в `backend/prisma/drift.json` есть причина).
2. `Db` → два implementation-а за тем же интерфейсом: `SqliteDb` (sync) и `PgDb` (async). Переход делает
   `db.all()` etc. возвращающими Promise **сначала в тестах**, потом в рантайме; `db.tx()` — `BEGIN IMMEDIATE`
   против `BEGIN; SELECT pg_advisory_xact_lock(...)` для crank-щелки.
3. ~~Диалект — 77 мест из таблицы §2, механически пофайлово, с тестом на файл.~~ **Сделано в коде** (2026-09-17):
   текст запросов собирается в `backend/src/sql.ts`, скан-тест `backend/test/sql.test.ts` не даёт конструкциям
   вернуться; см. «Статус шва» в §2. Осталось в этом пункте только то, что переезжает вместе со схемой (DDL,
   `PRAGMA`, seed-строка).
4. `timestamp`-колонки: у нас почти всё хранится unix-секундами в `INTEGER`. Мигрировать числом (`to_timestamp(x)`)
   и оставить внешний контракт в секундах — иначе клиент начнёт получать ISO вместо чисел, а это ломает
   `fmtDate`/`fmtTimeAgo` на 11 локалей.
5. Тесты: `:memory:` остаётся для юнитов (быстрые, без docker), контрактные (`api.test.ts`) — против контейнера.
6. Наблюдаемость: `/readyz` и `ingest_lag_slots` уже есть; добавить `pg_stat_activity` и время применения пачки — в те же метрики.

## 6. Критерий выбора (коротко)

| Условие | A | B |
|---|---|---|
| запуск, soak, первые недели | ✔ достаточно, и оно уже настроено | избыточно |
| > 1 реплики API с общими лимитами | лимиты уже в Redis (`backend/src/redis.ts`, ключ — `clientIp`: один клиент = одно ведро) — выдерживает | ✔ |
| аналитика/отчёты SQL-запросом, ad-hoc | `events_raw.data` как TEXT+json_extract, больно | ✔ `jsonb` |
| 5 000 rps чтений (цель из `docs/06` §4, LT-1) | кэш + один писатель — на пределе | ✔ |
| время до mainnet | 0 | +1–1.5 недели с двойной записью |

Рекомендация этого документа: **на запуск — A** (это не «временно и само пройдёт», а конфигурация с понятным порогом переключения), с обязательными двумя условиями: внешний диск с
снапшотами, включённый `BACKUP_S3_URI` (иначе RPO = «сколько прошло с последнего hourly») и живые
алерты `BackupStale`/`BackupFailing` на самом факте снятия (SEC-B49 — иначе этот RPO никем не проверяется), и
зафиксированный триггер перехода в B: ≥ 2 реплики API *или* следующая фича требует ad-hoc SQL-отчёт *или* p95
записи упёрся в `busy_timeout`. Проще перейти на B по триггеру, чем строить B к дате, которую никто не
назначал.

## 7. Что уже сделано, чтобы любой из вариантов не начинался с нуля

`npm run schema:check` (prisma ⇄ DDL, гейт в `verify` и CI) · `backend/.env.example` + `ops/deploy/.env.example`
без дрейфа · `ops/backup/sqlite-backup.sh` + `Dockerfile.backup` (снимок с проверкой `integrity_check` на копии, статус-файл `last_success_ts`/`consecutive_failures` и алерты `BackupStale`/`BackupFailing` — SEC-B48/SEC-B49) · `:memory:` в 24 из 28 файлов тестов бэкенда (файловая БД — только там, где проверяется сам файл:
`chip-index.test.ts`, `ops.test.ts`, `replay.test.ts`) ·
`/healthz` vs `/readyz` с лагом индексатора · метрики `ingest_lag_slots`/`events_backlog`/`crank_*` ·
Redis-стор лимитов (ключ — канонический `clientIp`: один клиент = одно ведро независимо от написания
адреса, SEC-B42) и `EVENT_BUS=redis` (то, что делает вариант A жизнеспособным при 2+ репликах; шина не
блокирует старт API при недоступном Redis — ограниченная подписка и откат до внутрипроцессной, видимые
как `event_bus_redis`/`EventBusDegraded`, SEC-B40).
