# Готовность GUTTERCAPS к запуску

**Проверено: 29 сентября 2026.** Ветка `arena/01a0ea01-guttercaps`, базовый commit `50f2f1cf7662589adbfee2481ac22e90b836d57a` + текущие незакоммиченные изменения.

## Вердикт

**К публичному запуску с реальными деньгами — пока не готово.**
Локальные сборки, тесты клиента/API и UI-проверки дают хорошую основу для подготовки тестового стенда. Они не доказывают, что покупка, выдача NFT, продажа, награды и восстановление работают в целевой сети и на production-инфраструктуре.

Для демонстрации интерфейса mock-сборка пригодна. Для закрытого devnet-тестирования нужно подготовить реальные программы, инфраструктуру и тестовые кошельки. Для mainnet остаются технические и операционные условия ниже.

**Проверки возраста и географии оставлены выключенными по решению владельца.** Они не включались обратно, юридический build-blocker не восстанавливался. Авторизация, admin, CSRF и privacy restrictions сохранены.

### Браузерные проверки: точный результат

В основном desktop-Chromium прогоне: **56 PASS, 2 FAIL, 15 SKIP** из 73 сценариев.
Два падения были в RU/ID при проверке живой смены языка уведомления: оно успевало исчезнуть по обычному TTL 4,5 секунды до assertions на загруженной машине.

Тест исправлен через Playwright Clock: время останавливается после загрузки данных, проверяются тот же DOM-узел, перевод и числа, затем время продвигается на 4,5 секунды и проверяется штатное исчезновение. UI-таймер приложения не менялся. **Повторный прогон всех 7 сценариев уведомления — 7 PASS.**

Отдельный nonmock UI-контур ошибок кошелька/API: **14 / 14 PASS**. Запросы и подписи перехватываются тестом; это не реальные операции в сети. Для параллельных проверок использованы разные output-каталоги: первая попытка с общим каталогом дала ошибки записи trace, после разделения финальные прогоны завершились успешно.

Таким образом, **72 уникальных браузерных сценария подтверждены по совокупности прогонов** (58 mock + 14 nonmock с перехватом). Полный единый прогон после исправления таймера не повторялся. **Один реальный devnet wallet-loop остаётся SKIP.**

Проверены семь языков, публичные страницы, авторизованные экраны, модальные окна, числа, юридические тексты, обращения, ошибки, live translation и серьёзные/критические axe-нарушения на выбранных денежных экранах. Тесты меняют ширину экрана; это не проверка настоящего Android-кошелька/MWA или всех браузеров.

## 2. Найдено и исправлено в этой проверке

### 2.1 Общий verify не проходил после локализации

- `packages/economy/scripts/sync-check.ts` искал удалённый `const STAKING` в `errors.ts`.
- `tests/security/anchor-invariants.test.ts` аналогично искал старые массивы всех четырёх программ.

Теперь читается настоящий `client/src/chain/errorCatalog.json`. Сверяются **имена и порядок вариантов ошибок**, а не только количество строк. Security-тест также требует непустой перевод для каждого ключа во всех семи языках. Совместное использование одного перевода одинаковыми ошибками допустимо. Проверки не отключены и не ослаблены.

### 2.2 Nginx терял защитные заголовки на HTML

В `ops/deploy/nginx.conf` локальный `add_header Cache-Control` у `/index.html` отменял наследование серверных `add_header`, включая CSP, X-Frame-Options и nosniff. SPA deep links переходят именно на этот HTML. Та же проблема существовала в locations assets/fonts; health использовал локальный Content-Type.

Cache-Control перенесён в server scope через `map $uri`; локальные overrides удалены, health использует `default_type`. Регрессионный тест проверяет наследование и падает при возвращении старой конструкции.

**Ограничение:** это проверка конфигурации и её семантики, не HTTP smoke реального nginx-контейнера. Docker/nginx отсутствуют в среде, загрузить nginx из Debian mirror не удалось из-за сетевых ошибок. Перед запуском обязательны `nginx -t` и проверка HTTP-заголовков `/`, `/index.html`, deep link, assets, 404 на реальном образе и через TLS/CDN.

### 2.3 API Dockerfile использовал несовместимый импорт TS

В `ops/deploy/Dockerfile.api` smoke-команда импортировала workspace экономики через обычный Node 22.13 без TS loader. Воспроизведено на **точной версии 22.13.0**: `ERR_UNKNOWN_FILE_EXTENSION` для `packages/economy/src/index.ts`.

Добавлен `--import tsx` — тот же production loader, который уже использует API. Повтор на Node 22.13 успешен, найдено четыре SKU. Добавлен регрессионный тест с мутацией и проверкой, что `tsx` находится в production dependencies.

Последний полный `verify` прошёл после nginx-исправления; после финальной правки Dockerfile отдельно прошли **136 security-тестов** и исполнение build-step на Node 22.13. Production Docker build всё ещё требуется.

## 3. Что мешает платному публичному запуску

### P0-A. Mainnet program IDs и релизные артефакты не готовы в проверяемом состоянии

`npm run program-ids -- status` подтверждает совпадение копий ID, но показывает **unverified** для четырёх программ. `npm run program-ids -- guard-mainnet` завершается ошибкой: все четыре mainnet ID являются заглушками. `programs/program-ids.json` и `ops/deploy/images.env` в checkout отсутствуют.

**Закрытие:** провести церемонию реальных program IDs в защищённой среде, назначить upgrade authority/pauser/treasury, собрать артефакты с правильными feature flags, зафиксировать freeze manifest, проверить IDL/байткод/authority, получить deploy images по digest. Не генерировать временные production-ключи ради зелёного теста.

### P0-B. Deployment-конфигурация не заполнена и сборка образов не подтверждена

`npm run ops:buildenv -- --check` вернул **8 ошибок**: отсутствуют RPC, четыре program ID и CG/USDC/SKR mint values. В локальном дереве только `.env.example`, не реальные конфигурации. Это нормально для защиты секретов, но не свидетельство готового окружения.

Последние три `images.yml` run в GitHub завершились ошибкой. На последнем проверенном run падение — в шаге `assemble the build env from compose (it refuses to guess)`. Полные логи не удалось загрузить из-за сетевого EOF, поэтому конкретная причина удалённого отказа не приравнивается автоматически к восьми локальным ошибкам.

**Закрытие:** задать реальные network/mint/RPC/DAS/доменные значения через конфигурацию и secret storage; собрать и запустить три контейнера, выполнить probes, проверить клиент без mock, WebSocket, SIWS и TLS. Наличие секретов на внешнем сервере не проверялось — сервер не предоставлен.

### P0-C. Не подтверждена реальная денежная/NFT-петля, включая Bubblegum V2

GitHub devnet smoke выглядит зелёным, но annotation прямо говорит:

> DEVNET_RPC_URL not set — devnet smoke skipped (T-D-03/T-D-04 pending)

Настоящий browser wallet-loop также пропущен. Успех mock-тестов не доказывает успешную покупку или выдачу NFT.

Клиентский compressed-pack pipeline уже реализован. Но приёмка Bubblegum V2/DAS в целевой сети не подтверждена; `docs/11-bubblegum-v2-migration.md` оставляет release gates открытыми, backend требует `BUBBLEGUM_V2_ENABLED=1` после их выполнения. Старый `open_pack` намеренно закрыт `CompressedMigrationRequired` — это не резервный production-механизм. Документ миграции содержит исторические формулировки: наличие/отсутствие отдельных функций нельзя определять только по его вводному абзацу.

**Закрытие:** на devnet доказать buy → reveal → compressed mint → DAS → register → finalize; затем продажу/покупку, staking/unstaking, fusion, PvP wagers/settlement, rewards и timeout/cancel/refund. Проверить восстановление после закрытия вкладки, сбоя RPC/DAS и рестарта crank. Не просто переключить V2-флаг ради старта API.

### P0-D. Операционная готовность и управление средствами не подтверждены

В checkout нет свидетельств настройки и финансирования операторских ключей, мультиподписи/pauser, treasury, reward/battle/burn workers, Pyth pusher и его счетов. Default `WORKERS=crank,pyth` **не включает reward/battle/burn**: для всех заявленных функций нужен осознанно настроенный комплект воркеров и ключей.

Нужны: рабочие RPC + WS + DAS, Switchboard/Pyth, Turnstile (или отдельное осознанное решение), SESSION_SECRET, CORS/SIWS domains, HTTPS/cookies, ADMIN_WALLETS, постоянная БД, мониторинг, доставка алертов и дежурный.

**Закрытие:** staging smoke всех воркеров, проверка балансов и authoritative account bindings, внешние probes и тест доставки каждого критического алерта. Ключи не передавать в чат и не коммитить.

### P0-E. Нет подтверждения приёмки рисков paid/mainnet эксплуатации

Проверяемые материалы не содержат завершённого независимого аудита именно release-кандидата, подписанной приёмки Bubblegum V2, отчёта о длительном devnet soak и полной production-нагрузке. План проекта предусматривает 14 дней / ≥10 000 паков; локальные unit-тесты не закрывают этот критерий.

**Закрытие:** зафиксировать кандидат, провести согласованную security-приёмку с закрытием Critical/High, нагрузку и длительный прогон; проверить backup/restore и rollback на фактической топологии. Восстановление должно учитывать privacy ledger, чтобы не вернуть удалённые данные.

## 4. Дополнительные риски и условия

### Зависимости

Свежий `npm audit`: **21 finding — 1 critical, 10 high, 5 moderate, 5 low**. Это число затронутых пакетов, включая транзитивные цепочки, не 21 независимая production-уязвимость.

Production-only: **4 high, 0 critical**, все из цепочки `bigint-buffer` / `GHSA-3gc7-fjrx-p6mg`. `npm run audit:gate` проходит **по существующему исключению**, а не потому, что проблем нет. В `scripts/audit-gate.ts` риск принят до 2027-03-31 с обоснованием ограниченных размеров input и отсутствия native addon в образах. Предпосылки надо подтвердить на готовом образе.

Critical в полном дереве относится к Vitest UI server; есть также advisories dev/build-инструментов Vite/Lighthouse и зависимостей. Открытый Vitest UI не запускался. Нужен контролируемый план обновления с регрессией, не `npm audit fix --force` и не откат SPL SDK на несовместимую древнюю версию.

### CI, производительность и масштабирование

Основной CI run на базовом commit — success, Rust/SBF/localnet jobs успешны. Исходники programs/tests-localnet/Anchor.toml/Cargo.lock здесь не менялись, но локально Rust/Anchor/Solana toolchain отсутствует: **повторной местной компиляции программ не было**. Текущие незакоммиченные изменения клиента/API не покрыты тем GitHub run.

В том же CI run Lighthouse job **failure**, скрытый за `continue-on-error`. Причина по доступным annotations не установлена. Бюджет JS PASS не заменяет исправленный Lighthouse и измерения на мобильном устройстве.

Backend использует SQLite, не работающий Postgres adapter. Возможен осознанный single-instance запуск с постоянным volume и проверенным восстановлением; заявлять multi-instance production на основании Prisma schema нельзя.

### Оператор и международный запуск

Оператор, реальные support/privacy contacts, правовые основания и рынки не определены; `LEGAL_REVIEWED=false`. Реализованы обращения/ответы и ограниченные privacy workflows, не автоматические выплаты и не полное удаление данных из blockchain/backups.

Age/geo-off — намеренное решение владельца, **не дефект и не основание снова вводить build-blocker**. Но это также не разрешение на платные случайные паки/PvP/NFT/вознаграждения во всех странах. Нужны реальные операторские решения, обработка обращений, расписание retention и обязанности по выбранным рынкам. Основателей можно не выставлять публичным брендом, но вымышленный оператор/контакт недопустим.

### Если запуск включает dApp Store

В `dapp-store/PORTAL_CHECKLIST.md` ещё не закрыты publisher/contact, подписанный APK, production URLs и минимум четыре approved store captures. Для обычного web-staging это не самостоятельный блокер; для публикации в магазине — отдельная приёмка. Реальный Android/MWA не проверялся.

## 5. Рекомендуемый порядок дальше

1. **Подготовить devnet/staging, не mainnet:** оператор безопасно задаёт домен/хостинг/RPC/DAS и ключи; никаких секретов в переписке.
2. Подготовить и проверить настоящие program IDs, mint/tree/collection/accounts, сетевые pins и права управления; заполнить deploy config.
3. Собрать контейнеры после текущих исправлений. Проверить nginx headers, auth, probes, worker health, алерты, backup/restore и rollback.
4. Пройти реальную петлю и аварийные сценарии всех включённых функций, завершить V2 release gates. Проверить мобильные кошельки.
5. Закрыть Lighthouse, зависимости/исключения, нагрузку, soak и независимую security-приёмку; назначить поддержку и обработку возвратов/privacy.
6. Зафиксировать проверенный release-кандидат и immutable artifacts. Отдельно принять решение о mainnet/публичном платном запуске на основании фактов.

**Сейчас следующий разумный этап — подготовка полноценного тестового развёртывания и реальная devnet-приёмка, а не открытие платного mainnet для пользователей.**
