# Фьюжн отвечает 3003: `fuse_compressed_claims` и версия chip_core в кластере

**Дата:** 2026-10-14 · **Кластер:** devnet · **Программа:** `chip_core`
`J68G8KrbLTSdi68LHr9Kkw1YbRRHv3uBPirWCd5Xt13V` · **Код:** Anchor `AccountDidNotDeserialize` = 3003 = `0xbbb`

## 1. Симптом

```
Program log: Instruction: FuseCompressedClaims
Program 11111111111111111111111111111111 invoke [2]
Program 11111111111111111111111111111111 success
Program log: AnchorError occurred. Error Code: AccountDidNotDeserialize. Error Number: 3003.
Program J68G8KrbLTSdi68LHr9Kkw1YbRRHv3uBPirWCd5Xt13V consumed 38055 of 399700 compute units
```

Клиентский тост: `chip_core: Не удалось десериализовать аккаунт [3003]`
(`client/src/chain/errors.ts` → `failures.anchor_3003`).

## 2. Как читать этот лог: виноват не тот аккаунт, который кажется

`Program 111…` — это не «какой-то системный аккаунт», а `init` результата: Anchor создаёт
`result_claim` (`seeds = ["compressed_claim", owner, nonce]`) через CPI в системную программу.
Строка `success` после него — это ответ на вопрос «какие аккаунты уже прочитаны».

В Anchor 0.31 сгенерированный `try_accounts` делает **сначала всю десериализацию**
(`deser_fields` в `lang/syn/src/codegen/accounts/try_accounts.rs`), а **потом** констрейнты —
и `init`-поля живут внутри фазы констрейнтов, перед access-чеками. Значит, к моменту CPI
`create_account` уже раскодированы все именованные аккаунты `FuseCompressedClaims`:

| аккаунт | тип | может ли дать 3003 |
|---|---|---|
| `config` | `Box<Account<GameConfig>>` | да, но тогда CPI не случился бы |
| `ledger` | `Box<Account<VaultLedger>>` | то же |
| `result_meta` | `Box<Account<CollectionMeta>>` | то же |
| `result_claim` | `init` — только что создан, тела ещё нет | нет |
| `cg_mint` | `Account<Mint>` (anchor_spl) | **нет**: `spl_token::state::Mint::unpack` → ошибка SPL, не Anchor |
| `owner_cg` | `Account<TokenAccount>` (anchor_spl) | **нет**: то же самое |

3003 выпускает только `#[account]`-дерив:
`AnchorDeserialize::deserialize(&mut data).map_err(|_| ErrorCode::AccountDidNotDeserialize)`
(`lang/attribute/account/src/lib.rs`). anchor_spl-типы в этом не участвуют, чужой владелец дал бы
3007, а чужой дискриминатор — 3002 (и то и другое напечаталось бы **до** CPI).

Остаётся единственная десериализация после этого CPI — **три материала из
`remaining_accounts`**, которые хендлер читает через
`CompressedMintClaim::try_deserialize_compat`.

## 3. Почему это говорит о версии программы, а не об аккаунте

`try_deserialize_compat` (programs/chip_core/src/state.rs) умеет ровно три вещи:

| размер аккаунта | что сделает этот чекаут | что сделает строгий `Account<CompressedMintClaim>` |
|---|---|---|
| 139 (текущий layout: 8 + 131) | OK | OK |
| 138 (поколение до `founder`) | OK — дописывает нулевой байт | **3003** |
| < 138 | `InvalidChipState` (кастомная ошибка) | **3003** |
| тело с битым `Rarity`/`bool` | 3003 | 3003 |

Последнюю строку программа сама по себе получить не может: `rarity` пишется как вариант enum'а,
`bool` — как 0/1. Значит, наблюдаемый 3003 на материале — это **строгий decode**, то есть
в кластере стоит chip_core **старше фикса от 2026-10-12** (SECURITY.md, «CompressedMintClaim,
compat read/write»: строгие слоты заменены на `UncheckedAccount` + `try_deserialize_compat`
в стейкинге, маркете, claim-CPI и «плюс the fusion material paths»).

Стыкуется с документами: последний **задокументированный** деплой devnet — **2026-10-03**
(`WATCHTOWER_HANDOFF.md`, раздел «Окружения» и блок B1), а компат-правки датированы
2026-10-12/13. Живые клеймы devnet созданы до `founder` — ровно тот случай, который фикс и
лечит («live Devnet claims … sit one byte short of `INIT_SPACE`»).

## 4. Как проверить за две минуты (не гадая)

```bash
# по подписи упавшей транзакции: сам достаёт 3 материала из ix 2 (аккаунты 9..12)
npm run claims:doctor -- --sig <signature> --rpc https://api.devnet.solana.com

# или по явным PDA
npm run claims:doctor -- --claims <pda1>,<pda2>,<pda3>

# байты программы в сети vs локальная сборка
npm run verify-deploy -- onchain --cluster devnet --rpc <RPC_URL>
```

Скрипт (`scripts/claim-doctor.ts`, без зависимостей, только `fetch` + JSON-RPC) печатает по
каждому клейму размер, расшифрованные поля и две колонки — «этот чекаут» и «строгая сборка» —
плюс слот последнего деплоя `chip_core` из `ProgramData`. Ожидаемая картина:

```
138 байт  [legacy-short]
   этот чекаут (compat):   OK (…) — compat дописывает нулевой `founder`
   строгий decode:         3003 AccountDidNotDeserialize

ВЕРДИКТ [stale_program]: … в кластере стоит chip_core старше фикса от 2026-10-12 —
                           пересоберите и задеплойте его.
```

`--selftest` прогоняет все поколения на синтетических байтах и встроен в `npm run verify`
(шаг 22 из 32).

## 5. Лечение

```bash
npm run mac:devnet          # этапы update → … → build → deploy → setup
```

Этап `deploy` (`scripts/mac-devnet.sh`) сам решает, что делать: программу, чьи байты уже лежат
в devnet, пропускает; выросшую — сперва расширяет (`solana program extend`); буфер переиспользует.
После redeploy `try_deserialize_compat` читает 138-байтовые клеймы, а `write_compat` пишет их
**той же длиной** — аккаунт не переаллоцируется, старые клеймы остаются пригодными для фьюжна,
стейкинга, маркета, `cancel_compressed_claim` и `close_expired_claim`.

Проверка после деплоя: повторить фьюжн и/или `npm run claims:doctor -- --sig <новая подпись>` —
все три материала должны уйти в `legacy-short` с колонкой «OK» у текущего чекаута.

## 6. Чего redeploy не исправит

Если doctor покажет `legacy-older` (короче чем на 1 байт — поколение до `lock_until`/`origin`),
компат-правка его **не** спасёт: `try_deserialize_compat` дополняет только один байт и отвечает
`InvalidChipState`. Такие клеймы нельзя сплавить ни на какой сборке — нужна отдельная миграция
(пере-`init` или закрытие через `close_expired_claim`), и это уже другая задача.

## 7. Почему это повторится, если ничего не менять

Каждый аппенд поля в `CompressedMintClaim` делает все ранее созданные аккаунты короче текущего
layout — и каждая сборка без компат-чтения ломает их на всех путях сразу. Контроль, который
ловит сам факт расхождения: `npm run verify-deploy -- onchain …` (сравнивает байты) и
`npm run claims:doctor` (сравнивает раскладку аккаунтов) — оба стоит гонять после каждого
деплоя, а `npm run state:layout` не даст сдвинуть layout молча.
